# Distribution and automatic updates

A push to main of the public repository `ota-takeru/gitlab-desktop` publishes a signed Windows NSIS release automatically after checks, except when the change touches only files that are not part of the app. The distributed app checks for updates at launch and every 6 hours while visible. It installs and restarts automatically when there is no unsaved input or send in progress and no activity for 2 minutes. The update notice's "Later" postpones it.

## GitHub settings

Set these values in the public repository.

| Type | Name | Content |
| --- | --- | --- |
| Repository variable | `TAURI_UPDATER_PUBLIC_KEY` | The public key generated by `tauri signer generate`. Store it as one line with no line breaks |
| Repository secret | `TAURI_SIGNING_PRIVATE_KEY` | The private signing key. Do not commit it to the repository or paste it in chat |
| Repository secret (optional) | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | The password set on the private key |

Generate the private key in a safe local place and register only the public key as `TAURI_UPDATER_PUBLIC_KEY`. Actions passes this repository variable to the signing script as the `TAURI_UPDATER_PUBKEY` environment variable. Do not add steps that print the private key or password to GitHub Actions logs. The public key, the distribution URL and the signed NSIS files are public.

## Release steps

A push to main makes Actions create a tag and publish after the checks. The version is decided in one of two ways.

- Push without changing the version: Actions raises the patch version by one (for example 0.4.0 to 0.4.1), pushes a `Release v<version>` commit to main, and publishes that commit. Your local main is then one commit behind, so run `git pull --ff-only` before the next work.
- Raise the version first and push: that version is published as it is. To raise the minor version or higher, for example for a new feature, run `npm run version:bump -- minor` (`patch` / `major` / `x.y.z` also work). It updates `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock` and `src-tauri/tauri.conf.json` together; commit the result.

A push whose changes are only in `docs/` and `*.md` is not published. To create a tag by hand, you can also use this:

```powershell
$version = "0.1.0"
git tag "v$version"
git push origin "v$version"
```

The release workflow validates the tag and stops if the three versions do not match or the tag does not point to the checked-out commit. For a push to main, it publishes in the same run the version if it changed compared with the commit before the push, and the automatically raised patch version if it did not. The `ci.yml` checks and the signed build run in parallel, and only the publish job, after both succeed, pushes the version commit and the tag. The publish job proceeds only after confirming that the commit to be tagged has the same tree as the source that was built. An existing tag is never reused. If a tag for the automatically raised patch version already exists, or if main advanced through another push during the checks, it stops without publishing. A version commit that Actions pushes with `GITHUB_TOKEN` does not start a new workflow, so publishing does not chain. `scripts/release-config.mjs` reads only the public key from the Actions repository variable and generates a temporary Tauri config that contains the fixed URL below and the NSIS settings.

`https://github.com/ota-takeru/gitlab-desktop/releases/latest/download/latest.json`

The build job creates the NSIS setup file and the signature file, and `scripts/updater-manifest.mjs` generates `latest.json`. The publish job uploads these three to the same public GitHub Release. The Rust build output is saved as main's cache with `Swatinem/rust-cache` to skip recompiling dependency crates next time. You can also rerun an existing `v<version>` tag by choosing it with `workflow_dispatch` on GitHub's Actions page. That run also verifies that the tag matches the version and points to the checked-out commit.

A push to main that changes only documentation, tests (unit, Playwright and Rust test modules) and their baseline images, test and lint settings, and `.github/` (CI and Dependabot) runs only the checks and does not release. The decision is made by `isOutsideApplication` in `scripts/release-main.mjs`. Changes to dependencies (`package.json` and lock files) and build settings (`vite.config.ts` and `tauri.conf.json`) affect the app and are released. Every other push and merge to main is subject to the automatic release above. Pushing a `v*` tag and rerunning an existing tag with `workflow_dispatch` are also available.

## App behavior

`UpdatePanel` checks once at desktop launch and checks again every 6 hours only while the window is visible. The browser preview does not call Tauri commands and shows updates as not configured. The Rust `check_app_update` gets the available version and release notes from the fixed HTTPS source. When an update is found, `download_app_update` downloads it in the background and verifies the signature, but does not install it. Installing and restarting happen through `install_app_update` only when the user presses "Restart to update", and never automatically. The real client screen watches for unsaved input and sends in progress, and enables `autoInstallAllowed` only when it is safe. While there is unsaved input or a send in progress, this button is also disabled.

The frontend does not receive a URL, public key or secret. The update source is fixed in the Tauri config generated at distribution build time, and IPC goes only through the typed wrapper in `src/lib/updater.ts`. Nothing stores GitLab credentials or the update signing key in localStorage, browser state or logs.

While an update downloads or applies, a dialog that cannot be closed blocks input and posting. Even if an expired login resets the per-account screens, this dialog and the update process stay. If the update fails, the app shows an error and returns to normal use.

## Local verification

In v0.2.0, the wait for saving the device's unsent comments also completes right before an update is applied. If saving fails, the update stops and the text is kept. Even after the recovery screen is shown again, the update waits while input kept in memory remains.

You can generate only the signing config by setting the public key in an environment variable temporarily. Run it in a way that leaves no private key value in command history or logs.

```powershell
$env:TAURI_UPDATER_PUBKEY = '<public-key>'
node scripts/release-config.mjs
node --test scripts/release-config.test.mjs
```

The generated `src-tauri/tauri.release.conf.json` is a temporary file for signing and is excluded from Git. Keep the private key outside the repository and sign with the GitHub Actions repository secret. Tauri's update signature and Windows Authenticode signing are different mechanisms. The current distribution has the update signature, and it does not use a corporate code signing certificate.

When Actions succeeds, check that the Release's Assets include the following.

- `latest.json`
- The Windows NSIS setup file
- The `.sig` for the setup file

Until `latest.json` is published, the app's check result is "Couldn't check for updates" or stays at the current version. The update path assumes that an artifact that fails signature verification never proceeds to installation.
