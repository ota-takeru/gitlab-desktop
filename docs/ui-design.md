# UI設計と変更ルール

状態: 製品UIの設計案。既存テーマと画面は初期基盤であり、ここに示す全ての共通部品が実装済みではない。

## UIモックで比較・確認する方針

2026-09-30のモックは、日常的にMRを連続レビューする作業画面を起点にする。低彩度のグレーを土台に、選択と主操作だけに控えめな青緑を使う。差分の追加/削除・状態色はそれぞれの意味に限定する。大きいカードの繰り返しより、薄い区切りと揃った行で情報を並べる。

- 通常幅: ナビゲーション、MR一覧、選択したMRの詳細を横並びにする。一覧から次のMRへ移る操作を短くする。
- 狭幅: ナビゲーションを縮小し、一覧と詳細を切り替える。差分を常時三列に押し込まない。
- 詳細: タイトル・状態・操作を上部に揃え、議論/変更/概要の順にタブを並べ、MRを開いた直後は議論を表示する。変更はファイルを選んで読み、関連する議論を同じ文脈で確認する。
- 検索: プロジェクト探索と過去MR検索を独立した入口にする。タイトル/説明とMR状態の条件を明示する。
- レビュー: 本文入力、下書き、返信、解決、承認の操作位置と状態表示を共通化する。

追加方針（2026-09-30）:

- プロジェクト一覧からは、そのプロジェクト専用の画面を開く。名称・namespace・説明を簡潔に示し、現在/過去のMRをプロジェクト内で検索する。MR詳細から戻っても対象プロジェクトと絞り込み条件を維持する。
- 変更タブの上部に、比較対象を選ぶ横向きのタイムラインを置く。先頭は「MR全体」、続いて古い順にコミットを並べる。コミットを選ぶと、その親からの変更だけを表示し、SHAと件名で対象を識別できるようにする。MR全体の行番号で付けた議論を、コミット差分へ誤って重ねない。
- 議論を左端の既定タブとし、コメント本文と返信をすぐ読める領域を確保する。概要は必要なときに説明全文と付帯情報を確認する参照画面とする。CI・承認数・変更ファイル数は短い一列にまとめ、大きな統計カードを追加しない。
- 返信・解決・コメント入力は議論タブにまとめ、返信時には入力欄へ移る。概要に議論や入力欄を重複表示しない。新規コメント・下書きはMRごとに保持し、概要や変更を見て戻っても本文を失わない。コメント本文と返信本文は同じ可読性を確保する。

モックは`#mock`で開く独立したプレビューとする。架空データを使うことと未接続を常時表示し、投稿・承認はローカルの操作シミュレーションに限定する。画面上の件数はfixtureと一致させる。実GitLab接続、ディスクへのキャッシュ保存、性能改善が実装済みであるとは表示しない。

この段階で確認するのは情報密度、画面の役割、操作順、一覧と詳細の関係、明暗テーマ、キーボードと狭幅での扱いやすさ。配色や密度を調整して基準を決めてから、接続機能の実装へ進む。サンプルの軽快さを実データの性能検証の代わりにはしない。

実装したモックの基準値はナビゲーション152px（手動折りたたみ・1100px以下で48px）、MR一覧314px、差分ファイル欄160px。狭幅では一覧/詳細を切り替え、ファイル選択を上部へ移す。本文・コード13px、補助情報11pxをテーマで定義し、見出し以外の過度な太字を避ける。追加/削除の背景色と文字色は明暗それぞれの専用トークンを使う。操作中の内容はメモリ上だけで保持し、リロードでリセットする。

### 日常利用のための画面枠

アプリ名は小さな一行表示に留め、ロゴの装飾・副題・「Workspace」「Reference」のグループ見出しを置かない。主要な移動先はアイコンと短い一行ラベルを持つ36px高の行とする。ナビゲーションは折りたたみ可能とし、狭幅では自動でアイコン表示にする。選択中の画面は選択状態と各画面の見出しで示す。

内容を繰り返す上部の「Review workspace / …」バーは設けず、作業内容をウィンドウ上端から表示する。UIカタログなどの補助機能は下部へまとめる。未接続・サンプルデータの表示は24px高の下部ステータスバーに集約し、ナビゲーションを折りたたんでも常に確認できるようにする。本文・コメントの文字は小さくせず、画面枠の余白と重複情報を減らす。

### コミットタイムラインの配置

タイムラインは「変更」タブの直下、ファイル一覧とコード差分の上に置く。コードの横幅を減らさず、ファイルを切り替えても比較対象が見える構成にする。先頭の「MR全体」は集約表示であり、その後のコミットは古い順。コミットの差分は常に親からの変更とする。

各項目は短いSHAと件名を持ち、長い件名は省略してツールチップで全文を確認する。項目が多くても帯を複数行にせず、横スクロールと送りボタンで移動する。左右矢印で選択を移動し、HomeでMR全体、Endで末尾コミットへ移る。選択中の項目は色と選択表示で識別でき、比較元と比較先もタイムライン直下に示す。

### ファイル全体の表示

ファイル見出しの近くに「差分 / ファイル全体」を置く。「ファイル全体」は抜粋差分をつなぎ合わせず、選択した版の変更後の内容を先頭から末尾まで表示する。MR全体を選んだ場合はMRの最新状態、コミットを選んだ場合はそのコミット時点の内容とし、SHAを表示して区別する。

表示モードは同じMR内のファイル・コミット切り替えで維持する。全文は一列の行番号と通常のコード表示を使い、差分の削除行や追加記号を混ぜない。既存の行コメントマーカーは差分側で表示する。新規コメントは差分・全文どちらからも、ファイルと旧/新側・行・SHAを指定して入力できる。全文未取得と空ファイルは異なる状態として示し、未取得の際に抜粋を全文と表示しない。将来の実接続でもファイル取得とキャッシュをコミットSHAに紐づけ、表示中の版と最新ブランチの内容を混在させない。

## 体験の優先順位

1. 現在の接続先、プロジェクト、検索対象がすぐ分かる。
2. 一覧を見ながら比較でき、詳細から戻っても文脈が残る。
3. データがない、未取得、更新中、古い、取得に失敗した、を区別できる。
4. マウスでもキーボードでも日常操作を繰り返せる。
5. MR・差分・議論が多くても、入力・切替・スクロールを止めない。キャッシュ表示後も更新状況が分かる。

画面ごとに新しい装飾を考えるのではなく、検索・一覧・詳細・設定という4種類の構造を再利用する。大きなヒーローや統計カードを既定のトップ画面にしない。

## レイアウトの基準案

| 要素 | 初期値/規則 |
| --- | --- |
| サイドバー | 通常224 CSS px。狭幅では縮小/折り畳み |
| 上部バー | 48 CSS px。接続先と文脈、検索入口 |
| ページ余白 | 16/24。横幅に応じて固定パターンで選ぶ |
| 一覧行 | compact 40、二行表示56を共通variantにする |
| 操作部品 | 通常32〜36高、最小24以上の操作領域を確保 |
| 文字 | 本文14、補助12、見出し18/22。diffはmonospace 13を出発点 |
| 余白 | 4px単位の4/8/12/16/24/32 |
| 角丸 | 小4、標準8。画面ごとの任意変更は禁止 |
| 色 | canvas/surface/text/border/actionと状態色。意味を持たない強い色を増やさない |
| 動き | 必要な状態変化だけ、100〜160ms程度。reduced-motionに従う |

これらは実データの一覧で確かめて固定する値。アクセント色は暫定で、色だけで状態を伝えない。未接続はニュートラル、通信失敗はerror、更新中はprogressとして区別する。ライト/ダークは同じレイアウトと情報階層を使う。

## 検索画面

上から「検索対象と入力」「フィルター」「検索結果と取得範囲」。プロジェクト検索とMR検索はタブで分け、どちらを検索しているか曖昧にしない。全状態/未マージ等の初期条件を隠さない。

結果行はタイトルだけでなくnamespace/project、MR番号、状態、作者、更新時刻を示す。同名プロジェクトや別プロジェクトの同じMR番号を見分けられるようにする。本文の全文を一覧で取得・表示しない。空結果には適用条件と解除方法を示す。

「全30件」と「30件取得」は区別する。サーバー検索、以前の検索結果、保存済みデータ内の検索は明示的に切り替える。検索結果の順序は使用したAPIのsort条件に従い、関係のないローカル履歴を混ぜて一つのランキングにしない。

## レビュー画面と大量データ

MR詳細は議論・変更・概要のタブを共通にし、ファイル選択、位置、展開状態を戻る操作で復元する。タイトル/説明の検索とコメント表示を混同しない。変更タブは選択ファイルを中心に表示し、解決済み議論は折り畳む。追加読み込みと省略状態を隠さない。

通常のレビュー操作は、全体/行コメント、返信、自分のコメント編集・削除、解決/再開、下書き公開、承認/取消。本文入力・保存・送信状態はReviewComposerに統一する。承認状態はコメント送信状態と分ける。「確認済みファイル」はローカル進捗と明記し、差分版が変わったら再確認を促す。

下書き一覧にはローカル保存とサーバー保存を区別して示す。公開する本文と件数を確認でき、Webで作成した下書きを暗黙に公開しない。複数公開の一部成功は項目ごとに表示する。投稿結果不明は失敗と区別し、確認前に再送へ誘導しない。

キャッシュがあれば即座に内容を出し、更新中に全画面をSkeletonへ戻さない。投稿・解決で変わるスレッドだけを更新し、一覧位置や入力本文を維持する。権限失効時はキャッシュ表示を続けて迂回しない。

長い一覧・差分・議論は仮想化する。可変高の本文でもスクロール位置が飛ばないこと、キーボードで未描画項目へ移動できること、編集中の下書きが消えないことを確認する。詳細な性能目標と負荷規模は[全体設計](architecture.md)第14節に従う。

コメントの種類、未公開レビュー、編集・削除と実接続で必要な機能の境界は[コメント・レビュー対応方針](comment-review-parity.md)に従う。入力中の下書きとレビューへ追加済みの未公開コメントを区別し、公開ダイアログには追加済みの内容だけを含める。Markdownの書式ツールとプレビューは本文表示と同じコンポーネントを使う。

## キーボード・フォーカス

- Ctrl+K: 移動/検索入口。Esc: パネルを閉じる、元の操作要素へフォーカスを戻す。
- Enter: 検索を適用、選択した項目を開く。テキスト入力中にグローバルショートカットを横取りしない。
- Tab: 可視の操作要素を論理順に移動。フォーカスを色だけでなく輪郭でも示す。
- 詳細を開いたら見出しへ、戻ったら元の行へフォーカスを復元する。
- 表の矢印キー操作は一覧部品のパターンとして実装する。単なる行全体クリックに依存しない。
- 非同期更新はaria-liveで控えめに通知し、定期更新で大量の読み上げを発生させない。

一覧を再取得するたびにスクロール位置や選択を初期化しない。行が対象から外れた場合はその理由を示し、別の行へ黙って選択を移さない。

## AI実装で守る変更手順

1. 新機能の前に、既存の画面パターンと共通部品で表現できるか確認する。
2. 機能の状態表を作る。正常時だけの画面を完成としない。
3. 新しい共通部品・variantを作ったらUIカタログに状態例を追加する。
4. テーマ・型・lint・代表動作テストを通す。
5. 明暗、狭幅/通常幅、長い日本語・長いパス、キーボード操作を確認する。
6. 共通部品の見た目を変えた場合は代表画面のスクリーンショット差分を確認する。

静的チェックは、現在の色直書き・直接HTTP検出に加え、直接invokeをIPC層以外で使わない規則を追加する。画面単位のMUIテーマ作成を禁止する。色や寸法の全てを正規表現だけで保証するとは考えず、共通部品とレビューを併用する。

スクリーンショット基準はプロジェクト一覧、過去MR検索、MR概要、diff、議論、接続エラーの代表状態に絞る。OS・フォント・WebView2バージョンを記録し、レンダラー更新による差と意図しないレイアウト差を区別する。データfixtureは匿名化した固定データを使う。
