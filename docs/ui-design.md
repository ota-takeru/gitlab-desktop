# UI design and change rules

Status: design proposal for the product UI. The existing theme and screens are an initial foundation; not every shared component described here is implemented.

## Comparing and checking with the UI mock

The 2026-09-30 mock starts from a work screen for reviewing MRs one after another every day. It uses low-saturation gray as the base and a restrained teal only for selection and the primary action. Diff add/delete colors and status colors are limited to their own meanings. Information is laid out with thin dividers and aligned rows rather than repeated large cards.

- Normal width: the navigation, the MR list and the details of the selected MR sit side by side. Moving from the list to the next MR takes few steps.
- Narrow width: the navigation shrinks, and the list and the details switch. The diff is not squeezed into three permanent columns.
- Details: the title, status and actions are aligned at the top, the tabs are ordered Discussion, Changes, Overview, and Discussion is shown right after an MR opens. In Changes, the reader selects a file and checks the related discussions in the same context.
- Search: finding projects and searching past MRs are independent entry points. The conditions for title/description and MR state are explicit.
- Review: the position and state display of the text input, draft, reply, resolve and approve actions are shared.

Additional policy (2026-09-30):

- Both the project list and the project name in the MR details open a screen dedicated to that project. Next to the project name in the heading are the tabs "Merge requests", "Branch" and "Code". Code shows the branch selection (the default branch at first) and the location breadcrumb, then folders first in name order; selecting a file shows it in the same place with line numbers and syntax highlighting. A submodule is not opened; only its name and kind are shown. The branch, folder and opened file are kept in the URL, and Back returns to the folder it was opened from. Branches are listed by most recent update, with the name, default/protected/merged, and the latest commit (short SHA, title, author, time). Selecting a row shows the MRs whose source is that branch in the project's MR list (the "Open in GitLab" action is outside the row). The filtered branch is shown as a tag in the conditions of the MR list; removing it or selecting the "Merge requests" tab again returns to the initial state of the project's MR list. Moving from a branch to the MR list stays in the history, and Back returns to the branch list. The screen shows the name, namespace and description briefly, and searches current/past MRs within the project. Returning from the MR details keeps the project and the filter conditions.
- At the top of the Changes tab is a horizontal timeline for choosing the comparison target. The first item is "Entire MR", followed by the commits in chronological order. Selecting a commit shows only the changes from its parent, and the target is identified by SHA and subject. Discussions placed at line numbers of the entire MR are not wrongly overlaid on a commit diff.
- Discussion is the leftmost default tab and reserves an area where comment bodies and replies can be read at once. Overview is a reference screen for checking the full description and additional information when needed. CI, the approval count and the changed-file count are gathered in one short row; no large statistics cards are added.
- Replying, resolving and writing comments are gathered in the Discussion tab. The reply box opens inside the thread being replied to and keeps its text separate from the new-comment box at the bottom. Closing it with Esc or "Close" keeps the text. Overview does not repeat discussions or input boxes. New comments and drafts are kept per MR, and the text is not lost when the reader looks at Overview or Changes and comes back. Comment bodies and reply bodies have the same readability.

The mock is a standalone preview opened with `#mock`. It always shows that it uses fictional data and is not connected, and posting and approving are limited to local simulations of the actions. The counts on screen match the fixture. It does not claim that a real GitLab connection, disk caching or performance improvements are implemented.

At this stage, the mock is checked for information density, the role of each screen, the order of operations, the relationship between list and details, light and dark themes, and ease of use with the keyboard and at narrow widths. The colors and density are adjusted to set the baseline before the connection features are implemented. The lightness of the sample does not replace performance checks with real data.

The baseline values of the implemented mock are navigation 152px (48px when collapsed manually or at 1100px and below), MR list 314px, and diff file column 160px. At narrow widths the list and details switch, and file selection moves to the top. Body and code text are 13px and secondary information is 11px, defined in the theme, and excessive bold outside headings is avoided. The added/deleted background and text colors use dedicated tokens for light and dark. Content being edited is kept in memory only and resets on reload.

### Screen frame for daily use

The app name stays a small single line, with no logo decoration or subtitle. The navigation holds only destinations (screens) and the tabs of open MRs. From the top, the order is Merge requests, Projects, and the tabs of open MRs (pinned, open). Merge requests is one search screen, and the user's own MRs (review requests, assigned, created) are switched with chips under the search box. Notifications are not a place, so they open from the notification button above Settings as a temporary overlay on the screen, with cards stacked from newest to oldest. Notifications for the same MR (such as a mention per comment) are stacked into one card that shows the content of the latest one and "n more", with up to 2 edges of the cards behind it visible. Opening a card moves to the target MR and marks all notifications for that MR as read (completes the GitLab To-Dos). The read marks are sent without blocking operations on the opened MR. "Mark all as read" in the heading fetches notifications up to 10 pages (1000 items), not only the displayed page, marks them as read 4 at a time, and refetches the list only once at the end. It reports the number of failed or unknown results. The next page loads when scrolling gets near the end (with the keyboard, "Load more"), up to a maximum of 10 pages displayed. A count with further pages is shown as "n or more". While the navigation is collapsed, resting the pointer on the notification button does not temporarily widen the navigation. When a notification is opened, the temporarily widened navigation returns to collapsed, and the notification is shown against the right edge of that width. While it is open, resting the pointer does not widen the navigation. Notifications are the open MR To-Dos in GitLab that announce events (mention, CI failure, unmergeable, approval request, manually marked and so on). Assigned and review requested are not included, because they are states that can be seen with the chips in the MR list and remain until the MR closes. The count is not a corner badge but a small tag with a subdued background. When expanded, only the number is placed at the end of the row; when collapsed, a tag with a bell and the number is placed at the icon position (9+ for 10 or more, and + when there are further pages). With no unread notifications, the bell is empty. The old `#client/todos` maps to the initial view of the MR list. A list of recently opened MRs is not provided, because it overlaps with the tabs of open MRs (the old `#client/recent` and `#client/pinned` map to the initial view of the MR list). Pressing a chip puts that "You" condition (the reviewer, assignee or author is the user) into the search box as a condition tag, replacing the other two. Pressing it again or the tag's ✕ removes it. Choosing from all MRs limits the state to Open. When the only condition is a single "You" condition (search term, state and sort order are allowed), the heading is, for example, "Assigned to me", and the MRs are grouped by approval status. Other conditions such as people, labels and branches, and saved searches, can be combined on the same screen. At startup the MR list is the search of all MRs (or the first list of the previously saved tab order, if there is one). The action to open from a URL is the action button at the right of the MR list heading. MRs are pinned from the sidebar tab, the MR details and the rows of the MR list; there is no list screen of pinned MRs. A pinned row always shows the pin button, and showing and removing the pin use the same component. "Merge requests" in the navigation returns to the list with the conditions last viewed. Icons match the meaning of the label, and "Pinned" is used only for MRs and matches the pin icon. The project shortcut is called "Favorites" and uses a star icon. The bottom of the navigation combines the account (avatar and username) and Settings into one item, and the settings screen holds connection, appearance (follow system / light / dark), auto-fetch and notifications, app updates, keyboard shortcuts and stored data. The navigation can be collapsed, and at narrow widths it automatically shows icons only. Opening an MR does not collapse it automatically. The width can be changed by dragging the right edge, and while collapsed, resting the pointer on it temporarily overlays the whole navigation. Only the tab section scrolls, and the place items and Settings are always in a visible position. The selected screen is shown by the selected state and each screen's heading, and while an MR is open, the tab of that MR, not a navigation place, is in the selected state.

There is no top "Review workspace / …" bar that repeats content; the work content is shown from the top edge of the window. Auxiliary features such as the UI catalog are gathered at the bottom. The not-connected and sample-data indications are consolidated in a 24px-high bottom status bar, so they stay visible even when the navigation is collapsed. The text of bodies and comments is not made small, and the margins of the screen frame and duplicated information are reduced.

### Screen layout of the implemented client (2026-10-09, revised 2026-10-13)

The implemented client was rebuilt into the layout decided in the mock, reviewing MRs one after another while watching the list. The colors, components and placement of operations were also revised to fit this layout. On 2026-10-13, because opened MRs can be switched with the sidebar tabs, the three panes that placed the list and details side by side were dropped, and the layout was changed to show either the list or the MR details at full width.

**Users.** The user link of the connected account and the author names in comments and MR details open an in-app user screen. As on the project screen, the tabs next to the name switch between "Created by me" and "Projects". MRs start with all states and are searched with the author fixed. Projects cover the personal namespace and do not include those inside groups. When content is not shown because of the profile's private setting or viewing permission, the empty list explains the reason. The screen uses the existing list components, and returning from the MR details restores the search conditions and display position.

**GitLab URLs.** Links in comments and descriptions and "Open from a GitLab URL" (Ctrl+O) open, in in-app screens, the MRs and users of the connected instance, and also projects (overview), branch lists, MR lists, folders (`/-/tree/`) and files (`/-/blob/`). A ref in a URL can contain `/`, so the folder or file that exists is taken, trying the shortest ref first. URLs not found as a project (such as groups) and other GitLab pages open in the default browser. An MR opens in the Overview tab, and when opened from a comment notification, in the Discussion tab. From outside the app, `gitlab-desktop://open?url=<GitLab URL>` opens the same screen (the installer registers the scheme, and if the app is running, the existing window is brought to the front and opens it). URLs other than the connected instance are ignored and not opened in the browser either.

**Layout.** To the right of the navigation (208px, 52px when collapsed), either the list or the MR details is shown at full width. An opened MR is represented by `mr=<projectId>-<iid>` in the URL, and the list is kept underneath the MR details without being shown, so the list's conditions, input and scroll position are kept when an MR is opened. The Back button of the details (Esc) returns to the list it was opened from. The button's name shows where it returns to, such as "Back to Review requests". For an MR opened from a list, Back goes back through the history to that list (including tab switches inside the MR and MR switches in the sidebar). So the browser's Back does not reopen the same MR. For an MR opened directly from a URL or another screen, the list is opened as a new history entry. Other MRs are reached with the sidebar tabs. The connection settings are a full-width page with no list. The loading, updating and saved indications are not inserted as rows that appear and disappear; their content is swapped in a place reserved from the start (a fixed-height status row for the list, "Saved · time" in the upper row of the MR header, and the startup connection check and MR loading inside the same frame as after completion). The old `#client/mr?...` form maps to the form opened from the initial view of the MR list.

**Use of width.** The main environment is a maximized window on a 27-inch 4K display at 200% scaling (effective 1920×1080), and removing empty space at wide widths is the priority. Opening an MR does not change the expansion or collapse of the navigation (an MR already uses the full width). The left and right margins of a pane are 16px. The Discussion tab has no maximum width, and when the width of the details pane (including the left and right margins) is 1200px or more, a 340px column is placed to the right of the threads, with the list of unresolved threads (selecting one moves to that thread) and the pending review pinned at the top. Below 1200px, it is one column of threads, pending review and new comment in that order, and the unresolved filter uses the switch at the top of the list. A thread with a line or file position shows the target code only while it is open. When the thread width is 960px or more, the comments are on the left (so the start of the line of sight is aligned in every thread) and the code on the right, and the code is pinned to the top while a long thread is read. When narrow, the code is placed above the comments. The code takes 4 lines before and 2 lines after the target line from the same hunk, and marks the target line with a line on the left edge. A comment on the MR's current head is shown as a diff from the same diff pages as the Changes tab (up to 10 pages). A comment on an old head, or on a file not in the diff pages, is shown from the file contents at the comment's commit, labeled "Code at the time of the comment". No code is shown for a comment on the whole file. For readability, comment text wraps at a maximum of 760px, while code blocks and tables use the full width of the thread. The diff search box is a one-line box with no description text, and the description goes in a tooltip.

**Colors.** The base is a neutral gray with reduced blue, and blue is limited to marks for primary actions, links and selection (a line on the left edge or an icon). The background of a selected row is a lighter gray, not blue. The surfaces change brightness in the order "navigation < list < details < card", with a step visible to the eye even in dark. The fill of the primary button is a blue dark enough for white text to be readable (`primaryFill`), separate from the bright blue for text and icons. Status indications are shown with an outline, not filled; Merged uses the same purple as GitLab, and the info color (such as CI running) is a light blue distinguishable from blue. The initial-letter avatar uses a pale color that is not a status color. In dark, the diff only tints the background and does not change the text color. The navigation places have their own colors (`palette.place`: Merge requests blue, Projects teal, notifications amber); the icon is always that color, and the selected row is lightly tinted with that color. The icons of lists belonging to a project (project, folder, README) are also the same teal. The place colors keep 4.5:1 against the navigation surface and 3:1 against the lightly tinted selection color, and the place is also shown by icon and name, not by color alone. All values are tokens in `src/theme.ts`, and `palette.surface` refers to the surface and selection color of each pane.

**How operations appear.** Only the primary action of each screen is always visible ("Approve" in the MR details). Refresh, Open in GitLab, pin and similar actions are icon buttons with tooltips, and the CI check, preview and pin of a list row appear when the mouse is over the row or on focus, while the pin is always shown on a pinned row (showing and removing the pin use the same component). With the keyboard, `J`/`K` in a list moves the row focus (Enter opens), and while an MR is open they open the previous or next MR of the list it was opened from. `/` goes to the list's search box, `Ctrl+K` to the search of all MRs, and `Ctrl+O` to open from a URL. Inside a list, the arrow keys and `J`/`K` move the focus.

**Shared components.** List panes are built from `PaneHeader` (a title or tabs that switch parallel lists, icon actions, search), `PaneStatus` (a one-line count and freshness) and `ListRow` (the whole row opens, and actions are outside the row). Empty and unselected states use `PaneEmpty`; MR state uses `MergeRequestStateIcon` in list rows and sidebar tabs and `StatusPill` with an icon in the header and preview; time uses `RelativeTime`, CI uses `PipelineStatus`, page navigation uses `Pager`, and each block of settings uses `SettingsSection`.

**Details pane.** Vertical scrolling is consolidated in the one details pane, and there is no vertical scrolling inside diffs, file bodies or input boxes (the diff pins the file heading, and the input box pins its formatting toolbar, below the MR header). Only the changed-file list pinned at the top and the right column of the Discussion tab scroll on their own. The header stays at the top while scrolling and lists, in order, the project, MR number and actions, the title, the status and additional information, and the tabs (Discussion with the unresolved count, Changes, Overview). The approval state is fetched when the details open, and the header can approve and revoke. The only primary action in the header is approve; merge, auto-merge, rebase, request changes, title, Draft, labels, milestone, and close/reopen are gathered in the "More actions" menu beside it. Mergeability (GitLab's judgment, in Japanese) is shown in the additional-information row, and merge, close, rebase and similar actions are sent through a confirmation dialog. Assignees and reviewers are always shown in the header and changed in a dialog from the edit button beside them. The app version is shown at the right of the bottom status bar. Posting confirmations and position-error warnings appear above the tab content so they are not buried at the end of a long discussion. The Overview tab lists the description and the author, branch, assignees, reviewers (with re-request review next to each person), approvals, labels and milestone. Labels are shown with `LabelChip`; GitLab's label color is used only for a small color swatch, and the text color follows the theme.

**Discussion.** Each comment lists the speaker's avatar, a one-line name and time, and the 14px body in that order, and unread is shown with a line on the left edge. The resolved state of a thread is shown and switched by one button at the top (pressing "Unresolved" makes it resolved, and pressing "Resolved" returns it to unresolved). A thread (line comment, resolvable, with replies) can be folded with the button at the top, and a resolved one starts folded. A single comment with no replies is not folded. The avatar uses GitLab's `avatar_url`, but the webview does not load image URLs directly. To show the same image as GitLab Web, Rust fetches images under `uploads/` of the connected instance with authentication, and the Gravatar that GitLab returns for users without an image (`/avatar/` of `gravatar.com` over `https://`) without credentials (PNG/JPEG/GIF/WebP, up to 256KB; the Gravatar fetch uses a concurrency slot separate from the GitLab API, so GitLab fetches and writes are not made to wait even in an environment that cannot reach the outside), and returns them as `data:` URLs. Other external hosts and failed fetches are shown as initials, and the CSP `img-src` is not changed. A line comment on a version earlier than the MR's latest gets "Outdated"; when it is displayed, the same file is read at the time of the comment and now, and it shows "Code matches" if the target line remains uniquely, "Code may have changed" in a warning color if it is not found, and "Cannot verify" if it cannot be determined (the reason is in a tooltip). File reads are shared per file and commit. If the file does not exist in the current version, the comparison of the MR's two versions (page 1) is used: a renamed file is matched by its new name, and a deleted file is "Code may have changed". Comments on deleted lines are not tracked.

**Loading more of the MR list.** The MR list does not page; it appends the next page (30 items) below when the end is near. With the keyboard, "Load more" at the end does the same. Changing the conditions returns to page 1, and pages loaded by scrolling are not kept in the URL. Up to 10 pages (300 items) are kept, and beyond that the screen asks the user to narrow by conditions. Auto-refresh runs only for page 1, and later pages are refetched with the refresh button. An MR that moved across a page boundary appears only once, at the position where it was first displayed. Rows off screen skip rendering, so scrolling does not get heavy as the count grows.

**Loading discussions and display position.** Discussions stay in chronological order but are loaded from the newest. The GitLab discussions API cannot specify the sort order, so the last page is found from `X-Total-Pages` of page 1 (Rust returns it as `totalPages` of the Snapshot), and the last page is fetched first. If the last page has fewer than 10 threads, the page before it is loaded as well. If the total page count is not returned, the pages are followed from the first as before. Up to 10 pages are fetched, and "Load earlier discussions" at the top or scrolling up widens toward older pages one page at a time. Auto-refresh runs every 60 seconds for the latest page and every 5 minutes for the loaded older pages. GitLab puts replies in the page that has the thread, so replies and edits by others to old threads are also shown this way. Old pages are also refreshed right after an operation on that thread, such as a reply or resolve.

When the Discussion tab opens, it shows the first unread comment if there are read comments and also unread ones, and the end of the thread of the latest comment on the first open or when there is no unread. The position is set once before rendering, after the threads and drafts are both fetched, so no intermediate position is shown. When older discussions are added above, or the threads above grow with an update, the position of the thread at the top edge of the screen is kept. Auto-loading of old pages happens only when the user scrolls. Returning from another tab goes back to the same visible position, and when an MR is reopened, it is again shown from the newest.

**Diff.** The display format is switched with the button in the file heading between "Inline" and "Side-by-side", and the choice is saved on this device. In side-by-side, the old side is on the left and the new side on the right, a run of deleted lines and the following run of added lines are matched one line at a time, and unchanged lines appear on both sides. Long lines wrap instead of scrolling horizontally, and the heights of the left and right rows are aligned. A comment is attached to the old line from the left side and to the new line from the right side, and an unchanged line gets one button on the right side that attaches at a position with both the old and new line numbers. Rows in the inline view are at least 22px, and the comment "+" button overlaps to the right of the line number. Multiple lines are selected only within the same hunk, with Shift+click from "+", dragging on line numbers, or Shift+↑/↓ on "+"; the selected lines are marked with a line on the left edge on the line-number side (also the line-number background in the inline view), and the input box opens below the last line. A range comment is placed below its last line, and the bottom of the thread shows "Comment on lines 12–15". "Hide whitespace" is a switch in the file heading and is saved on this device. Long lines also wrap in the inline view. Between hunks, the number of omitted lines is shown. The file list appears at the side only when the width of the details pane is 820px or more; when narrow, the reader moves with the previous/next buttons in the header and "n/total". A page has at most 600 lines, so rows are drawn with one set of styles on the container side, not with per-row styled components.

The light and dark themes follow the OS setting at first launch, and a choice switched manually is saved on this device.

### Commit timeline placement

The timeline sits directly under the "Changes" tab, above the file list and the code diff. This does not reduce the width of the code, and the comparison target stays visible when the file is switched. The first item, "Entire MR", is an aggregate view, and the commits after it are in chronological order. A commit's diff is always the changes from its parent.

Each item has a short SHA and a subject, and a long subject is truncated, with the full text in a tooltip. Even with many items, the strip does not wrap to several rows and moves with horizontal scrolling and step buttons. The left and right arrows move the selection, Home goes to Entire MR, and End goes to the last commit. The selected item is identified by color and a selected marker, and the comparison source and target are also shown directly under the timeline. Next to the display of the comparison source and target is the "Compare from version" selection, and choosing a past version shows the diff from that version to the latest as read-only (with a rebase note). "Local changes" to its right shows the difference between the linked clone's working tree and the MR's latest as read-only. If it is not linked, it shows a folder input box and "Choose folder…" (choosing links it immediately), and once linked, the folder, branch, HEAD and read time, with reload and unlink, are placed above the diff. "Whole file" and the expansion between hunks use the current contents of the working tree.

### Whole file display

Near the file heading is "Diff / Whole file". "Whole file" does not stitch excerpt diffs together; it shows the post-change content of the selected version from start to end. When Entire MR is selected, it is the MR's latest state, and when a commit is selected, it is the content at that commit, and the SHA is shown to tell them apart.

The display mode is kept when switching files and commits within the same MR. The whole text uses a single column of line numbers and normal code display, without the diff's deleted lines or added marks. Existing line comment markers are shown on the diff side. A new comment can be entered from either the diff or the whole text, specifying the file, old/new side, line and SHA. The whole text not yet fetched and an empty file are shown as different states, and when it is not fetched, an excerpt is not shown as the whole text. In the future real connection too, file fetching and the cache are tied to the commit SHA, and the displayed version is not mixed with the content of the latest branch.

## Experience priorities

1. The current connection, project and search target are clear at once.
2. The reader can compare while watching the list, and the context remains after returning from the details.
3. No data, not fetched, updating, stale and failed to fetch can be told apart.
4. Daily operations can be repeated with both mouse and keyboard.
5. Input, switching and scrolling do not stop even with many MRs, diffs and discussions. The update status is visible even after cached content is shown.

Instead of designing new decoration per screen, the four structures of search, list, details and settings are reused. A large hero or statistics cards are not the default top screen.

## Layout baseline proposal

| Element | Initial value/rule |
| --- | --- |
| Sidebar | 208 CSS px, 52 when collapsed. Collapses automatically at 1000px and below |
| Top bar | None. The connection is shown in the 24px bottom status bar, and the context in each pane's heading |
| Page margin | 16/24. Chosen by a fixed pattern according to the width |
| List row | compact 40 and two-line 56 are the shared variants. The MR list uses three lines of project, title and state (about 80) |
| Control | Normally 32 to 36 high, with an operable area of at least 24 |
| Text | Body 14, secondary 12, headings 18/22. Diff starts from monospace 13. Chips and small headings (overline) are 11 |
| Spacing | 4/8/12/16/24/32 in 4px steps |
| Grid | Line boxes, control heights and row heights are whole 4px steps (`grid` and `gridLine(n)` in the theme), so the text, chips and buttons in one row share pixel edges. Text variants have px line heights (caption 16, body2 20, body1 24, h1 24, code and diff rows 20), and icons use whole sizes (20/24/32, 18 in icon buttons). `npm run design:guard` rejects ratio line heights and heights of 16px and up that are off the grid. In development builds, Ctrl+Alt+G or `?grid` in the URL lays the grid over the window. At 125% display scaling a 1px border is drawn as one device pixel (0.8 CSS px); content after it stays on whole device pixels |
| Corner radius | Small 4, standard 8. Arbitrary per-screen changes are prohibited |
| Color | canvas/surface/text/border/action and status colors. No strong colors without meaning are added |
| Motion | Only necessary state changes, about 100 to 160ms. Follows reduced-motion. Only the completion of approve, merge and publishing a review paints the notification in the success color, and the check bounces while a ring expands (about 0.6 seconds, static under reduced-motion) |
| Icon | One icon per meaning, and one meaning per icon. State icons in a row are 16px. The mapping is below |

Icon mapping: project `Source`, directory `Folder`, file `InsertDriveFile`, parent folder `ArrowUpward`, branch `AltRoute`, Merge requests `RateReview`, notifications `NotificationsNone` (when there is unread, the filled `Notifications` and a count tag), Settings `Settings`, open from a URL and link `Link`, connect to GitLab `Login`, token renewal `Key`, refetch `Refresh`, open externally `Launch`, pin (MRs only) `PushPin`, favorite (projects only) `Star`, approved (state) `ThumbUpOutlined` (the user's own approval is the filled `ThumbUp`), Draft `EditNote`, unread `MarkChatUnread`, default branch `Home`, protected `Lock`, merged `CallMerge`, archived `Inventory2`, pending review `ScheduleSend`, notification kinds (assigned `AssignmentInd`, mention `AlternateEmail`, approval request `HowToReg`, review request `PersonSearch`, mark `BookmarkBorder`, CI failure `ErrorOutline`, unmergeable `Block`), approve (action) `Check`, success `CheckCircleOutline`, error `ErrorOutline`, warning `WarningAmber`, waiting `Schedule`, cancel, close and cancel job `DoNotDisturbAlt`, rerun job or pipeline `Replay`, run manual job `PlayArrow`, toggle file tree display `ViewSidebar`, tree view `AccountTree`, previous/next file `KeyboardArrowLeft/Right`, previous/next unresolved thread `KeyboardArrowUp/Down`. The resolved state of a thread is shown and switched by `ResolveToggle` (unresolved `RadioButtonUnchecked` / resolved `CheckCircle`).

**State is shown by shape and color rather than text.** To lower cognitive load, states lined up in list rows (MR state, Draft, CI, approval, unread, branch and project attributes) are not text chips but are shown with `StateIcon` (a 16px icon, with only a count added if needed). The state name stays in the tooltip and the name for assistive technology, and states are told apart by shape as well, not by color alone (the user's own approval is a filled icon, CI running spins, and it stops under the reduce-motion setting). Notification kinds, pending reviews on the diff, and the mergeability in the MR header are also icon-only, with the kind or reason in a tooltip. MR state and Draft add a short text to the icon in the header and preview.

These are values to be fixed after checking with lists of real data. The accent color is provisional, and state is not conveyed by color alone. Not connected is distinguished as neutral, a communication failure as error, and updating as progress. Light and dark use the same layout and information hierarchy.

| StatusBadge | Mapping of state and label, icon, color |
| DetailLayout / Section | Return to the list, tabs, primary and secondary information |
| DiffViewer / DiscussionThread | Line numbers, version, folding, position, fetch limit |
| CommitTimeline | The first Entire MR, commits in chronological order, SHA and subject, comparison source and target, switching the displayed file |
| ReviewComposer / DraftList | Text input, diff position, save status, publish target, partial success, unknown result |
| ReviewActionBar | Publish drafts, approve/revoke, availability by permission, version and reauthentication |
| FormField / Confirmation | Validation errors, sending, discard confirmation |

Not every MUI component needs a custom wrapper. Only repeated decisions are shared. `sx` in a feature is limited to placement, and when color, text, density or state display is added, it is reflected in a shared component or the theme.

## Search screen

From the top: "search target and input", "filters", "search results and fetched range". Project search and MR search are separated by tabs, and it is never ambiguous which one is being searched. Initial conditions such as all states / not merged are not hidden.

A result row shows not only the title but the namespace/project, MR number, state, author and update time. Projects with the same name and the same MR number in different projects can be told apart. The full body text is not fetched or shown in the list. An empty result shows the applied conditions and how to remove them.

"All 30" and "30 fetched" are distinguished. Server search, previous search results and search within saved data are switched explicitly. The order of search results follows the sort condition of the API used, and unrelated local history is not mixed into one ranking.

## Review screen and large data

The MR details share the tabs Discussion, Changes and Overview, and restore file selection, position and expansion state on Back. A search of the title/description is not confused with showing comments. The Changes tab is centered on the selected file, and resolved discussions are folded. Additional loading and truncated states are not hidden.

The normal review operations are overall/line comments, replies, editing and deleting one's own comments, resolve/reopen, publishing drafts, and approve/revoke. Text input, saving and send states are unified in ReviewComposer. The approval state is kept separate from the comment send state. "Viewed" files are labeled as local progress, and the reader is asked to check again when the diff version changes.

The draft list distinguishes local saves from server saves. The body and count to publish can be checked, and drafts created on the web are not published implicitly. A partial success of publishing several is shown per item. An unknown post result is distinguished from a failure, and the reader is not led to resend before checking.

With a cache, the content is shown immediately, and a full-screen Skeleton does not return during updating. Only the threads changed by a post or resolve are updated, and the list position and input text are kept. When permission expires, the cached display continues and is not bypassed.

Long lists, diffs and discussions are virtualized. Check that the scroll position does not jump even with variable-height bodies, that the keyboard can move to items not yet rendered, and that a draft being edited does not disappear. Detailed performance targets and load sizes follow section 14 of [Architecture](architecture.md).

The boundary between comment kinds, pending reviews, editing and deleting, and the features needed for the real connection follows the [comment and review parity policy](comment-review-parity.md). A draft being typed is distinguished from a pending comment already added to the review, and the publish dialog includes only what has been added. Markdown input defaults to rich input that shows the formatting in place, and can be switched to the Markdown view that edits the syntax directly. When rich input would change how the body renders (such as HTML), it opens in the Markdown view and does not rewrite the body without the user's action. The typography of rich input uses the same style as the body display.

## Keyboard and focus

- Ctrl+K: the entry for navigation/search. Esc: close a panel and return focus to the original control.
- Enter: apply the search term, or open the selected item. Conditions other than the search term (state, person, label, branch, updated date, project, group) are edited from "+ Add condition" or the tags and applied the moment they are chosen. Applied conditions, including the search term, are all shown as removable tags, and the sort order is not a condition, so it is chosen with a dropdown, not a tag. Global shortcuts (including Ctrl+K and Ctrl+O) are not intercepted while typing in a text input.
- ?: the shortcut list. In an MR, N/P move between unresolved threads and ]/[ between files.
- Tab: moves through visible controls in logical order. Focus is shown by an outline, not by color alone.
- When details open, focus goes to the heading, and on return, to the original row.
- Arrow-key operation of tables is implemented as a pattern of the list component. It does not depend on whole-row clicks alone.
- Asynchronous updates are announced modestly with aria-live, and periodic updates do not cause a large amount of reading aloud.

Each refetch of a list does not reset the scroll position or selection. When a row falls out of the target, the reason is shown, and the selection is not silently moved to another row.

## Change procedure for AI implementation

1. Before a new feature, check whether it can be expressed with the existing screen patterns and shared components.
2. Make a state table for the feature. A screen that works only in the normal case is not complete.
3. When a new shared component or variant is made, add state examples to the UI catalog.
4. Pass the theme, type and lint checks and representative behavior tests.
5. Check light and dark, narrow/normal width, long Japanese text and long paths, and keyboard operation.
6. When the look of a shared component changes, record this device's baseline with `npm run ui:snap` before the change, and check the screenshot diff of representative screens with `npm run ui:snap` after the change. If the diff is intended, rebuild the CI baseline images with a manual UI Preview run with `update_snapshots` and take them in (font rendering differs per device, so the CI baseline is made in CI). Sections of the UI catalog with a `catalog-*` id are captured automatically.

Static checks add, to the current detection of hard-coded colors and direct HTTP, a rule that direct invoke is not used outside the IPC layer. Creating a MUI theme per screen is prohibited. Not every color and dimension is assumed to be guaranteed by regular expressions alone; shared components and review are used together.

Screenshot baselines are limited to representative states of the project list, past MR search, MR overview, diff, discussion and connection error. The OS, font and WebView2 version are recorded, so differences from renderer updates can be told apart from unintended layout differences. Data fixtures use anonymized fixed data.
