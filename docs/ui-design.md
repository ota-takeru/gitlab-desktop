# UI design and change rules

Status: design proposal for the product UI. The existing theme and screens are an initial foundation; not every shared component described here is implemented.

## Where to make a visual change

| To change | Change it in |
| --- | --- |
| A colour | `tokens` in `src/theme.ts`; screens use the palette names |
| The size or line height of a kind of text | `typography` and `typeLines` in `src/theme.ts` |
| Button height or padding | `MuiButton` in `src/theme.ts`, with `size="dense"` and `variant="quiet"` as the other sizes. At their default sizes, buttons, single-line fields and toggles are all 32px, so check them together. A dense button is 24px and a dense field 28px |
| Field height or padding | `MuiOutlinedInput` in `src/theme.ts`, with `size="dense"` for toolbars. Screens do not reach into `.MuiInputBase-*` to re-size a field |
| A list's search field or order pull-down | `components/ConditionSearchField` and `components/PillSelect` |
| A line or frame | `hairline()`, `frame()` or `panelFrame()` from `components/hairline`, not `border` |
| How a row aligns | `Row`, `Bar` and `firstLine` from `components/Row` and `components/rows` |
| How a control meets a row's edge | `Bar` from `components/Row`, or `edgeRow` from `components/edges` on another row; a control's `--edge-inset` is in `src/theme.ts`, or on the control for a custom size |
| The placement of one element | `sx` on that element |
| A look that a second screen also needs | A component in `src/components`, with a sample in the UI catalog, instead of a copied `sx` |

A long JSX line is split when a change touches it; lines are not reformatted on their own. `npm run design:guard` checks the colour, type, line, row, edge and button-size rules, but not field re-sizing or copied `sx`, and in development `?grid` shows what sits off the grid. The reasons and layout values are in [Layout baseline proposal](#layout-baseline-proposal); colour values are in `tokens`.

## Comparing and checking with the UI mock

The 2026-09-30 mock starts from a work screen for reviewing MRs one after another every day. It uses low-saturation gray as the base and a restrained teal only for selection and the primary action. Diff add/delete colors and status colors are limited to their own meanings. Information is laid out with thin dividers and aligned rows rather than repeated large cards.

- Normal width: the navigation, the MR list and the details of the selected MR sit side by side. Moving from the list to the next MR takes few steps.
- Narrow width: the navigation shrinks, and the list and the details switch. The diff is not squeezed into three permanent columns.
- Details: the title, status and actions are aligned at the top, the tabs are ordered Discussion, Changes, Overview, and Discussion is shown right after an MR opens. In Changes, the reader selects a file and checks the related discussions in the same context.
- Search: finding projects and searching past MRs are independent entry points. The conditions for title/description and MR state are explicit.
- Review: the position and state display of the text input, draft, reply, resolve and approve actions are shared.

Additional policy (2026-09-30):

- Both the project list and the project name in the MR details open a screen dedicated to that project. Under the project name are the tabs listed in "Project screen" below. Code shows the branch selection (the default branch at first) and the location breadcrumb, then folders first in name order; selecting a file shows it in the same place with line numbers and syntax highlighting. A submodule is not opened; only its name and kind are shown. The branch, folder and opened file are kept in the URL, and Back returns to the folder it was opened from. Branches are listed by most recent update, with the name, default/protected/merged, and the latest commit (short SHA, title, author, time). Selecting a row shows the MRs whose source is that branch in the project's MR list (the "Open in GitLab" action is outside the row). The filtered branch is shown as a tag in the conditions of the MR list; removing it or selecting the "Merge requests" tab again returns to the initial state of the project's MR list. Moving from a branch to the MR list stays in the history, and Back returns to the branch list. The screen shows the name, namespace and description briefly, and searches current/past MRs within the project. Returning from the MR details keeps the project and the filter conditions.
- At the top of the Changes tab is a horizontal timeline for choosing the comparison target. The first item is "Entire MR", followed by the commits in chronological order. Selecting a commit shows only the changes from its parent, and the target is identified by SHA and subject. Discussions placed at line numbers of the entire MR are not wrongly overlaid on a commit diff.
- Discussion is the leftmost default tab and reserves an area where comment bodies and replies can be read at once. Overview is a reference screen for checking the full description and additional information when needed. CI, the approval count and the changed-file count are gathered in one short row; no large statistics cards are added.
- Replying, resolving and writing comments are gathered in the Discussion tab. The reply box opens inside the thread being replied to and keeps its text separate from the new-comment box at the bottom. Closing it with Esc or "Close" keeps the text. Overview does not repeat discussions or input boxes. New comments and drafts are kept per MR, and the text is not lost when the reader looks at Overview or Changes and comes back. Comment bodies and reply bodies have the same readability.

The mock is a standalone preview opened with `#mock`. It always shows that it uses fictional data and is not connected, and posting and approving are limited to local simulations of the actions. The counts on screen match the fixture. It does not claim that a real GitLab connection, disk caching or performance improvements are implemented.

The mock is a reference, not a second client (decided 2026-11-04). It opens only in development builds, and a change to the client needs no matching change in `src/components/mock` or `src/pages/MockApp.tsx`. The design guard checks only raw colours and direct network calls there, so its values are not an example to copy. The one exception is `MockMarkdown`, which despite its folder is the client's Markdown renderer and follows every rule, including the untranslated-text check.

At this stage, the mock is checked for information density, the role of each screen, the order of operations, the relationship between list and details, light and dark themes, and ease of use with the keyboard and at narrow widths. The colors and density are adjusted to set the baseline before the connection features are implemented. The lightness of the sample does not replace performance checks with real data.

The baseline values of the implemented mock are navigation 152px (48px when collapsed manually or at 1100px and below), MR list 314px, and diff file column 160px. At narrow widths the list and details switch, and file selection moves to the top. Body and code text are 13px and secondary information is 11px, defined in the theme, and excessive bold outside headings is avoided. The added/deleted background and text colors use dedicated tokens for light and dark. Content being edited is kept in memory only and resets on reload.

### Screen frame for daily use

The app name stays a small single line, with no logo decoration or subtitle. The navigation holds only destinations (screens) and the tabs of open MRs. From the top, the order is Merge requests, Projects, and the tabs of open MRs (pinned, open). Merge requests is one search screen, and the user's own MRs (review requests, assigned, created) are switched with chips under the search box. Notifications are not a place, so they open from the notification button above Settings as a temporary overlay on the screen, with cards stacked from newest to oldest. Notifications for the same MR (such as a mention per comment) are stacked into one card that shows the content of the latest one and "n more", with up to 2 edges of the cards behind it visible. Opening a card moves to the target MR and marks all notifications for that MR as read (completes the GitLab To-Dos). The read marks are sent without blocking operations on the opened MR. "Mark all as read" in the heading fetches notifications up to 10 pages (1000 items), not only the displayed page, marks them as read 4 at a time, and refetches the list only once at the end. It reports the number of failed or unknown results. The next page loads when scrolling gets near the end (with the keyboard, "Load more"), up to a maximum of 10 pages displayed. A count with further pages is shown as "n or more". While the navigation is collapsed, resting the pointer on the notification button does not temporarily widen the navigation. When a notification is opened, the temporarily widened navigation returns to collapsed, and the notification is shown against the right edge of that width. While it is open, resting the pointer does not widen the navigation. Notifications are the open MR To-Dos in GitLab that announce events (mention, CI failure, unmergeable, approval request, manually marked and so on). Assigned and review requested are not included, because they are states that can be seen with the chips in the MR list and remain until the MR closes. The count is not a corner badge but a small tag with a subdued background. When expanded, only the number is placed at the end of the row; when collapsed, a tag with a bell and the number is placed at the icon position (9+ for 10 or more, and + when there are further pages). With no unread notifications, the bell is empty. The old `#client/todos` maps to the initial view of the MR list. A list of recently opened MRs is not provided, because it overlaps with the tabs of open MRs (the old `#client/recent` and `#client/pinned` map to the initial view of the MR list). Pressing a chip puts that "You" condition (the reviewer, assignee or author is the user) into the search box as a condition tag, replacing the other two. Pressing it again or the tag's ✕ removes it. Choosing from all MRs limits the state to Open. When the only condition is a single "You" condition (search term, state and sort order are allowed), the heading is, for example, "Assigned to me", and the MRs are grouped by approval status. Other conditions such as people, labels and branches, and saved searches, can be combined on the same screen. At startup the MR list is the search of all MRs (or the first list of the previously saved tab order, if there is one). The action to open from a URL is the action button at the right of the MR list heading. MRs are pinned from the sidebar tab, the MR details and the rows of the MR list; there is no list screen of pinned MRs. A pinned row always shows the pin button, and showing and removing the pin use the same component. "Merge requests" in the navigation returns to the list with the conditions last viewed. Icons match the meaning of the label, and "Pinned" is used only for MRs and matches the pin icon. The project shortcut is called "Favorites" and uses a star icon. The bottom of the navigation combines the account (avatar and username) and Settings into one item, and the settings screen holds connection, appearance (follow system / light / dark), auto-fetch and notifications, app updates, keyboard shortcuts and stored data. The navigation can be collapsed, and at narrow widths it automatically shows icons only. Opening an MR does not collapse it automatically. The width can be changed by dragging the right edge, and while collapsed, resting the pointer on it temporarily overlays the whole navigation. Only the tab section scrolls, and the place items and Settings are always in a visible position. The selected screen is shown by the selected state and each screen's heading, and while an MR is open, the tab of that MR, not a navigation place, is in the selected state.

There is no top "Review workspace / …" bar that repeats content; the work content is shown from the top edge of the window. Auxiliary features such as the UI catalog are gathered at the bottom. The not-connected and sample-data indications are consolidated in a 24px-high bottom status bar, so they stay visible even when the navigation is collapsed. The text of bodies and comments is not made small, and the margins of the screen frame and duplicated information are reduced.

### Screen layout of the implemented client (2026-10-09, revised 2026-10-13)

The implemented client was rebuilt into the layout decided in the mock, reviewing MRs one after another while watching the list. The colors, components and placement of operations were also revised to fit this layout. On 2026-10-13, because opened MRs can be switched with the sidebar tabs, the three panes that placed the list and details side by side were dropped, and the layout was changed to show either the list or the MR details at full width.

**Users.** The user link of the connected account and the author names in comments and MR details open an in-app user screen. As on the project screen, the tabs next to the name switch between "Created by me" and "Projects". MRs start with all states and are searched with the author fixed. Projects cover the personal namespace and do not include those inside groups. When content is not shown because of the profile's private setting or viewing permission, the empty list explains the reason. The screen uses the existing list components, and returning from the MR details restores the search conditions and display position.

**Project screen.** A project is where the reader comes for context around a review: what changed lately, in which MR or commit, and what the code is now. The tabs under its name are, in order, Overview, MR, History, Code and Branches. Overview shows the README in full, with no excerpt and no scrolling of its own, and the project's description in the header. Beside the README (a 340px column pinned at the top when the pane is 1200px or more; above the README when narrower) are the latest 5 commits of the default branch and the 5 most recently updated open MRs, each with "Show all" leading to its tab. History lists the commits of a branch by day, newest first, and can be limited to a path. Code and History share the branch, so moving between those two tabs keeps it. "History of this folder" or "History of this file" in Code and the history button of a branch row open History with that path or branch. A commit opens at the pane's full width, with the list kept underneath, as an MR does: the title, the rest of the message, the short SHA, author and time, the related MRs, and the changes from its first parent in the same diff view as an MR, read-only. Back or Esc returns to the list, and `J`/`K` or the arrow buttons move to the older or newer commit of the list; a commit not on the list's current page has no such neighbours. "Show commit" in blame and line history opens this screen in the desktop app, and the commit screen has the button that opens it on GitLab when the project's URL is known.

**GitLab URLs.** Links in comments and descriptions and "Open from a GitLab URL" (Ctrl+O) open, in in-app screens, the MRs and users of the connected instance, and also projects (overview), branch lists, MR lists, folders (`/-/tree/`), files (`/-/blob/`), commits (`/-/commit/` with a full SHA) and a branch's history (`/-/commits/` with a ref in one path segment (`/` only as `%2F`) and no path; other forms are not handled as this screen). A ref in a folder or file URL can contain `/`, so the folder or file that exists is taken, trying the shortest ref first. URLs not found as a project (such as groups) and other GitLab pages open in the default browser. An MR opens in the Overview tab, and when opened from a comment notification, in the Discussion tab. From outside the app, `gitlab-desktop://open?url=<GitLab URL>` opens the same screen (the installer registers the scheme, and if the app is running, the existing window is brought to the front and opens it). URLs other than the connected instance are ignored and not opened in the browser either.

**Layout.** To the right of the navigation (208px, 52px when collapsed), either the list or the MR details is shown at full width. An opened MR is represented by `mr=<projectId>-<iid>` in the URL, and the list is kept underneath the MR details without being shown, so the list's conditions, input and scroll position are kept when an MR is opened. The Back button of the details (Esc) returns to the list it was opened from. The button's name shows where it returns to, such as "Back to Review requests". For an MR opened from a list, Back goes back through the history to that list (including tab switches inside the MR and MR switches in the sidebar). So the browser's Back does not reopen the same MR. For an MR opened directly from a URL or another screen, the list is opened as a new history entry. Other MRs are reached with the sidebar tabs. The connection settings are a full-width page with no list. The loading, updating and saved indications are not inserted as rows that appear and disappear; their content is swapped in a place reserved from the start (a fixed-height status row for the list, "Saved · time" in the upper row of the MR header, and the startup connection check and MR loading inside the same frame as after completion). The old `#client/mr?...` form maps to the form opened from the initial view of the MR list.

**Use of width.** The main environment is a maximized window on a 27-inch 4K display at 200% scaling (effective 1920×1080), and removing empty space at wide widths is the priority. Opening an MR does not change the expansion or collapse of the navigation (an MR already uses the full width). The left and right margins of a pane are 16px. The Discussion tab has no maximum width, and when the width of the details pane (including the left and right margins) is 1200px or more, a 340px column is placed to the right of the threads, with the list of unresolved threads (selecting one moves to that thread) and the pending review pinned at the top. Below 1200px, it is one column of threads, pending review and new comment in that order, and the unresolved filter uses the switch at the top of the list. A thread with a line or file position shows the target code only while it is open. When the thread width is 960px or more, the comments are on the left (so the start of the line of sight is aligned in every thread) and the code on the right, and the code is pinned to the top while a long thread is read. When narrow, the code is placed above the comments. The code takes 4 lines before and 2 lines after the target line from the same hunk, and marks the target line with a line on the left edge. A comment on the MR's current head is shown as a diff from the same diff pages as the Changes tab (up to 10 pages). A comment on an old head, or on a file not in the diff pages, is shown from the file contents at the comment's commit, labeled "Code at the time of the comment". No code is shown for a comment on the whole file. For readability, comment text wraps at a maximum of 760px, while code blocks and tables use the full width of the thread. The diff search box is a one-line box with no description text, and the description goes in a tooltip.

**Colors.** The base is a neutral gray with reduced blue, and blue is limited to marks for primary actions, links and selection (a line on the left edge or an icon). The background of a selected row is a lighter gray, not blue. The surfaces change brightness in the order "navigation < list < details < card", with a step visible to the eye even in dark. The fill of the primary button is a blue dark enough for white text to be readable (`primaryFill`), separate from the bright blue for text and icons. Status indications are shown with an outline, not filled; Merged uses the same purple as GitLab, and the info color (such as CI running) is a light blue distinguishable from blue. The initial-letter avatar uses a pale color that is not a status color. In dark, the diff only tints the background and does not change the text color. The navigation places have their own colors (`palette.place`: Merge requests blue, Projects teal, notifications amber); the icon is always that color, and the selected row is lightly tinted with that color. The icons of lists belonging to a project (project, folder, README) are also the same teal. The place colors keep 4.5:1 against the navigation surface and 3:1 against the lightly tinted selection color, and the place is also shown by icon and name, not by color alone. All values are tokens in `src/theme.ts`, and `palette.surface` refers to the surface and selection color of each pane.

**How operations appear.** Only the primary action of each screen is always visible. The MR details are the exception: their header shows its operations as labelled buttons (see "Details header actions"). Refresh, Open in GitLab, pin and similar actions are icon buttons with tooltips, and the CI check, preview and pin of a list row appear when the mouse is over the row or on focus, while the pin is always shown on a pinned row (showing and removing the pin use the same component). With the keyboard, `J`/`K` in a list moves the row focus (Enter opens), and while an MR is open they open the previous or next MR of the list it was opened from. `/` goes to the list's search box, `Ctrl+K` to the search of all MRs, and `Ctrl+O` to open from a URL. Inside a list, the arrow keys and `J`/`K` move the focus.

**Shared components.** List panes are built from `PaneHeader` (a title or tabs that switch parallel lists, icon actions, search), `PaneStatus` (a one-line count and freshness) and `ListRow` (the whole row opens, and actions are outside the row). Empty and unselected states use `PaneEmpty`; MR state uses `MergeRequestStateIcon` in list rows and sidebar tabs and `StatusPill` with an icon in the header and preview; time uses `RelativeTime`, CI uses `PipelineStatus`, page navigation uses `Pager`, and each block of settings uses `SettingsSection`.

**Details pane.** Vertical scrolling is consolidated in the one details pane, and there is no vertical scrolling inside diffs, file bodies or input boxes (the diff pins the file heading, and the input box pins its formatting toolbar, below the MR header). Only the changed-file list and the column of a file's table of contents, which stay below the MR header in the Changes tab, and the right column of the Discussion tab, scroll on their own. The header stays at the top while scrolling and lists, in order, the project, MR number and actions, the title, the status and additional information, and the tabs (Discussion with the unresolved count, Changes, Overview).

**Details header actions.** The approval state is fetched when the details open. On an open MR, the header's approve button becomes revoke once the user has approved. It becomes a retry button if the approvals fail to load.

The first header row has two sides.

The left starts with the back button when there is one. The project, the MR number and the icon tools for this page follow. These tools are copy link, open in GitLab, pin and refresh. The saved time comes last when the data is stale.

The right holds labelled actions, in this order:

1. Mark notification as read, when a notification is pending.
2. Approve, on an open MR.
3. Request changes, on an open MR whose reviewers include the user.
4. A button that follows the MR's state.
5. The "More actions" menu.

The state button is chosen by these checks, in order:

1. A closed MR gets reopen.
2. Any other MR that is not open, meaning merged or locked, gets no button.
3. An MR with auto-merge set gets cancel auto-merge.
4. While `detailed_merge_status` is `need_rebase`, the button is rebase, unless a rebase is already running or the head SHA is unknown. It appears whatever the user's permission, and GitLab refuses it when they may not rebase.
5. Otherwise the button is merge, which leads to the merge panel.

A merge can be sent only when `detailed_merge_status` is `mergeable`, the user has permission to merge and no rebase is running. The header's merge button reads "set auto-merge" while a pipeline is running or waiting to start and nothing else blocks the merge.

When neither a merge nor auto-merge can be sent, the merge button stays clickable, unless another write, other than a reaction or marking a notification as read, is running, or writes are locked (for example, while the result of a post is unknown). Its tooltip gives the reason. Clicking it leads to the merge panel.

The menu holds title, labels and milestone. On an open MR, it also holds Draft and close. When the source branch of an open MR is behind and GitLab does not require a rebase, it also holds an optional rebase.

At most one header button is primary (contained). Merge or set auto-merge is primary when two conditions both hold: it can be sent, and the user is not a reviewer or has already approved. Otherwise approve is primary until the user has approved. The retry button is not primary.

At narrow widths the right side of the first header row wraps to a second row rather than overflowing.

Mergeability (GitLab's judgment, in the app's language) is shown as an icon in the additional-information row, with the judgment as its tooltip. Clicking it leads to the merge panel. These actions are sent through a confirmation dialog: approve, revoke, merge, close, reopen, rebase, cancel auto-merge, Draft, request changes and re-request review. Assignees and reviewers are always shown in the header and changed in a dialog from the edit button beside them. The app version is shown at the right of the bottom status bar. Posting confirmations and position-error warnings appear above the tab content so they are not buried at the end of a long discussion. The Overview tab lists the description and the author, branch, assignees, reviewers (with re-request review next to each person), approvals, labels and milestone. Labels are shown with `LabelChip`; GitLab's label color is used only for a small color swatch, and the text color follows the theme.

**Merge panel.** Merging an open MR happens in `MergePanel` at the top of the Overview tab. It is not in the sticky header, so it takes no height from the other tabs. It is above the description, so a long description does not push it down. The header's merge button and the mergeability icon switch to the Overview tab and scroll to the panel. What belongs in the panel is the merge and what clears the way to it.

The panel starts with the same judgment as the header's icon. At most one button sits beside it:

- While auto-merge is set, the button cancels auto-merge, whatever the user's permission. The options and merge buttons are hidden.
- No button appears while GitLab is still checking, while a rebase is running, or when merge permission is false or unknown.
- Otherwise `mergeResolution` (in `mergeActions.ts`) picks the step from `detailed_merge_status`: `draft_status` marks ready, `need_rebase` rebases when the head SHA is known, `not_approved` approves, `discussions_not_resolved` and `requested_changes` open the discussion, and `ci_must_pass`, `ci_still_running` and `security_policy_pipeline_check` open the pipelines. Every other blocking status, known or not, opens GitLab.
- Approve is offered only when the user has not approved, writes are not locked, the head SHA is known and the approvals have loaded. When these do not hold, or a rebase cannot run, no button appears, and the panel does not send the user to GitLab instead. The app does not check whether the user is eligible to approve.

A rebase button appears below the judgment when the source branch is behind and GitLab does not already ask for a rebase, unless a rebase is running or the head SHA is unknown. It appears whatever the user's permission, and GitLab refuses it when they may not rebase.

A user with merge permission also gets the options and merge buttons, unless auto-merge is set. Without permission, or when it is unknown, the panel shows only the judgment and the cancel and rebase buttons above.

- Options: squash, delete the source branch, and an optional merge commit message. Squash cannot be changed when the project always or never squashes, or when the project settings are readable and the MR already asks for a squash. When they cannot be read, a note says the result can differ from the choice.
- Buttons: when auto-merge can be set, it is the primary button, and merge now sits beside it if a merge can also be sent. Otherwise there is one merge button, disabled unless a merge can be sent. Without a head SHA the buttons are disabled.

Approve runs the same write as the header's button. The merge, rebase, mark ready and cancel auto-merge run in `MergeRequestActions`, which stays mounted on every tab, so they share the header's confirmation and a rebase is followed after leaving the Overview tab. A merge is sent with the head SHA shown in the confirmation dialog. If the client has read a newer head by the time the dialog is confirmed, it sends nothing and says so; otherwise GitLab refuses the old SHA. Rebase and canceling auto-merge also stay in the header, as the state button or the menu, so they can be reached from any tab.

**Discussion.** Each comment lists the speaker's avatar, a one-line name and time, and the 14px body in that order, and unread is shown with a line on the left edge. The resolved state of a thread is shown and switched by one button at the top (pressing "Unresolved" makes it resolved, and pressing "Resolved" returns it to unresolved). A thread (line comment, resolvable, with replies) can be folded with the button at the top, and a resolved one starts folded. A single comment with no replies is not folded. The avatar uses GitLab's `avatar_url`, but the webview does not load image URLs directly. To show the same image as GitLab Web, Rust fetches images under `uploads/` of the connected instance with authentication, and the Gravatar that GitLab returns for users without an image (`/avatar/` of `gravatar.com` over `https://`) without credentials (PNG/JPEG/GIF/WebP, up to 256KB; the Gravatar fetch uses a concurrency slot separate from the GitLab API, so GitLab fetches and writes are not made to wait even in an environment that cannot reach the outside), and returns them as `data:` URLs. Other external hosts and failed fetches are shown as initials, and the CSP `img-src` is not changed. A line comment on a version earlier than the MR's latest gets "Outdated"; when it is displayed, the same file is read at the time of the comment and now, and it shows "Code matches" if the target line remains uniquely, "Code may have changed" in a warning color if it is not found, and "Cannot verify" if it cannot be determined (the reason is in a tooltip). File reads are shared per file and commit. If the file does not exist in the current version, the comparison of the MR's two versions (page 1) is used: a renamed file is matched by its new name, and a deleted file is "Code may have changed". Comments on deleted lines are not tracked.

**Loading more of the MR list.** The MR list does not page; it appends the next page (30 items) below when the end is near. With the keyboard, "Load more" at the end does the same. Changing the conditions returns to page 1, and pages loaded by scrolling are not kept in the URL. Up to 10 pages (300 items) are kept, and beyond that the screen asks the user to narrow by conditions. Auto-refresh runs only for page 1, and later pages are refetched with the refresh button. An MR that moved across a page boundary appears only once, at the position where it was first displayed. Rows off screen skip rendering, so scrolling does not get heavy as the count grows.

**Loading discussions and display position.** Discussions stay in chronological order but are loaded from the newest. The GitLab discussions API cannot specify the sort order, so the last page is found from `X-Total-Pages` of page 1 (Rust returns it as `totalPages` of the Snapshot), and the last page and the page before it are read together. The page before it is shown from the start only if the last page has fewer than 10 threads. Otherwise, the first "Load earlier discussions" or scroll up shows it. GitLab omits the total page count for a list of more than 10,000 records, and cache entries saved before the app recorded the count do not have it. In that case the last page is searched for with `X-Next-Page`. The page number doubles while pages have a next page. GitLab answers a page past the end with an empty list and no next page, and the range is then halved until a page with threads and no next page is found. If page 1 is empty, the search ends there and the list shows no discussions. These reads do not count toward the 10-page limit, and they run one at a time, so the list takes longer to appear. A page that cannot be read during the search shows as the discussion list's error, and the refresh button reads it again. The last page found this way then follows the same display rules as one found from `X-Total-Pages`. When a new page appears after the last page, the threads on screen stay until it is read. With a reported total, the new count names the page to read. Without one, no new search starts, and the following page is read. Pages added beyond that are then found one at a time. The page being read is read as often as the newest page, and a read that fails is not shown as an error and is tried again. It becomes the newest page once it is read, or without a reported total, once it has threads. Posting a comment, and checking a write whose outcome is unknown, read it together with the newest page. If a reported total moves so far that no page already read is left in the latest 10 pages counted from that total, the list shows as loading until one of those pages is read. The 10-page limit is the one exception to keeping the threads on screen. The oldest page leaves the list when the new last page is known, which with a reported total is before the new page is read, and without one is once the new page has threads. A page fetches 30 discussions. Those with only system notes are not shown, so a page can add fewer. Up to 10 pages (300 discussions) are fetched, and "Load earlier discussions" at the top or scrolling up widens toward older pages one page at a time. At that limit, a notice that points to GitLab for earlier discussions replaces the button. Auto-refresh runs every 60 seconds for the latest page and every 5 minutes for the loaded older pages. GitLab puts replies in the page that has the thread, so replies and edits by others to old threads are also shown this way. Old pages are also refreshed right after an operation on that thread, such as a reply or resolve. A discussion's comments are split into pages of 50, with previous and next buttons.

When the Discussion tab opens, it shows the first unread comment if there are read comments and also unread ones, and the end of the thread of the latest comment on the first open or when there is no unread. The position is set once before rendering, after the threads and drafts are both fetched, so no intermediate position is shown. When older discussions are added above, or the threads above grow with an update, the position of the thread at the top edge of the screen is kept. Auto-loading of old pages happens only when the user scrolls. Returning from another tab of the same MR goes back to the same visible position.

An MR's screen stays in memory after it is left, and an MR whose screen is still kept also goes back to its earlier position when opened again. The screens kept are the one on view, those of MRs with a sidebar tab and the 4 others most recently shown. While the list or settings is showing, no MR is on view. Then the 5 MRs most recently shown are kept besides those with a sidebar tab. The number of MRs kept is therefore the same as while an MR is on view. Under memory pressure, only the MR on view is kept, and MRs with a sidebar tab are not kept. While no MR is on view, only the MR shown last is kept. Memory pressure is defined at the end of [section 6 of the architecture](architecture.md#6-responsibilities-for-loading-updating-and-caching). When memory pressure starts, the other kept MR screens are unmounted at once. When memory pressure ends, those screens are not built again. A screen no longer kept is built again when it is opened, and its position is chosen by the unread rule in the first sentence of the previous paragraph.

**Diff.** The display format is switched with the button in the file heading between "Inline" and "Side-by-side", and the choice is saved on this device. In side-by-side, the old side is on the left and the new side on the right, a run of deleted lines and the following run of added lines are matched one line at a time, and unchanged lines appear on both sides. While wrapping is on, the heights of the left and right rows are aligned. A comment is attached to the old line from the left side and to the new line from the right side, and an unchanged line gets one button on the right side that attaches at a position with both the old and new line numbers. Rows in the inline view are at least 20px, and the comment "+" button overlaps to the right of the line number. Multiple lines are selected only within the same hunk, with Shift+click from "+", dragging from "+", or Shift+↑/↓ on "+"; the selected lines are marked with a line on the left edge on the line-number side (also the line-number background in the inline view), and the input box opens below the last line. A range comment is placed below its last line, and the bottom of the thread shows "Comment on lines 12–15". "Hide whitespace" is a switch in the file heading and is saved on this device. Wrapping is another switch in the file heading, on by default, for both formats, and is saved on this device. It is hidden in the whole-file view and while a Markdown diff shows its rendered form, as neither has diff rows to wrap. With wrapping off, each line stays on one row and the diff area scrolls sideways as one, so in side-by-side both sides move together. Shift and the mouse wheel scroll it with the pointer anywhere over the diff area. While the end of the diff is below the visible area of the details pane, its scrollbar stays at the bottom edge of that area. Otherwise it sits right under the last row. It is also there as an empty track when no line overflows, so it does not appear and disappear from file to file. Threads are as wide as the visible diff area and do not move when it scrolls sideways. In the inline view the line numbers do not move either; in side-by-side they scroll with the code. In side-by-side, lines opened from the omitted lines between hunks still wrap, because the width of each side is computed before they are opened. While wrapping is off, the toolbar of a comment editor does not stick under the file heading, because the diff area is its own scrolling box. This is an accepted limit: sticking it would need a different way to scroll. Between hunks, the number of omitted lines is shown. A summary above the file list and the diff shows the number of files in the list and their added and removed lines in total. A file missing from GitLab's list, as when GitLab cuts a long list short, is not in it. For the entire MR and for a comparison between versions, a warning above the diff says so. Each row of the file list shows the added and removed lines of that file. A listed file whose diff GitLab left out as collapsed or too large has no count in its row and is not in the total, and the summary says how many such files there are. When such a file is opened, the app tries to compare its two versions. If the comparison gives a diff, only its file heading shows a count. The row and the total stay as they were. When the two versions together are longer than 1,000,000 characters, the app does not compare them. Such a file then shows a warning line in the diff area in place of the diff. This is the same warning line as for a file that is not text or that takes too long to compare. With "Hide whitespace" on, the rows, the summary and the file heading do not count whitespace-only changes. The file list appears at the side only when the width of the details pane is 820px or more (1100px for a side-by-side diff) and the reader has not hidden it (saved on this device). The file-list button in the file heading (`ViewSidebar`) is there at every width. When the list fits at the side, it hides and shows the list. When the list does not fit, it opens the same list in a 360px popover, whatever the saved choice is. The popover closes when a file is chosen. With or without the list, the reader can move with the previous/next buttons in the file heading, and "n/total" shows the position when there are two or more files. A file's diff is not split into pages. It can hold many thousands of lines, so the cost of each row is kept small. Rows are drawn with one set of styles on the container side, not with per-row styled components. Rows render in pieces of 50. The first pieces render at once. The remaining pieces render in the background. A piece off screen skips layout and paint. The exception is a piece that holds a thread, a draft or an open comment editor. The editors and menus in such a piece must not be clipped. Syntax highlighting colors the whole new side, including unchanged lines. In side-by-side, the old side shows unchanged lines with the colors from the new side. On the old side, syntax highlighting colors only deleted lines. It reads each block of deleted lines together with up to 20 unchanged lines before the block. A string or comment that starts further up than those lines can therefore show wrong colors on the deleted lines. The app keeps the colors of the 4 files it most recently colored in full, up to 2,000,000 characters together. When the reader returns to the same diff of one of these files in any diff view, the first render colors it in full. The same holds when the tab is built again. When the kept colors go over 4 files or 2,000,000 characters, the app first lets go of the colors used longest ago. The colors of a file longer than 2,000,000 characters are not kept. In that case the app does not let go of the colors it has already kept. Files with no known language and Markdown shown rendered are not kept. When memory pressure starts, the app lets go of all kept colors. While memory pressure lasts, the app keeps colors again within the same limits. When a file's colors are not kept, the first render colors the first 50,000 characters of each side. On the old side, the 50,000 characters include the unchanged lines read with each block of deleted lines. The remaining text is colored between frames, in runs of the same size. This is meant to keep scrolling and typing working; the effect has not been measured. When every run has finished, all rows render again in the background with their colors. Each run is parsed on its own. A string or comment crossing two runs can therefore show wrong colors up to the end of the later run.

**File names in the diff.** File names stay on one line and do not wrap. A name too long for its place is cut with an ellipsis. In the file heading, the folders are in the `text.secondary` color and give way first, so `src/features/merge…DiffViewer.tsx` keeps the file's name. The end of the name is cut only when the name alone does not fit. The path, "n/total" and the line counts together come after the file-list and previous/next buttons and take 220px of the row. Controls after them that do not fit beside that move to the next row. If the group does not fit beside those three buttons, the group itself moves to the next row, and on a row narrower than 220px it shrinks. In the file list, in both the tree and the flat list, the end of the name is cut and the line counts and marks stay whole. In the flat list, a second line under the name shows the kind of change (with the old path for a renamed file) and the folder, and is cut the same way.

**File list width.** The width of the file list beside the diff can be changed by dragging its right edge. On that edge, the left and right arrow keys change it by 16px, Home goes to the narrowest and End to the widest, and a double click returns it to the default 240px. The width is saved on this device. It goes from 160px up to 600px, as far as 568px (848px for a side-by-side diff) remains for the diff beside it. When the pane narrows, the list becomes narrower than the saved width, down to 240px, and goes back to that width when the pane widens. The file-list popover stays 360px.

**Maximized diff.** A button at the end of the file heading lets the diff cover the whole window, over the navigation, the MR header and the commit timeline. This applies to every screen with a diff: an MR's changes, an MR's local changes (the local repository compared with the MR) and a commit's details.

The file list and the table of contents stay. Their width rules then use the whole window. The file list and the table of contents stick to the window's top instead of below the MR header. The covering view has its own vertical scroll.

The button is the only way in; no key enters it. Focus is not trapped, so Tab can reach the covered controls. This is an accepted limit.

The app's shortcuts still work. After a shortcut that moves to another screen, the screen it came from stays maximized.

The maximized state stays when the reader moves to another file or uses the view controls in the heading. It is not saved.

Moving to another commit or version creates the diff again, in the normal view. Coming back to a screen kept in memory finds it still maximized. A screen no longer in memory is created again in the normal view.

The button or Esc restores the view. Outside the maximized view, Esc leaves the screen. On an MR and on its local changes, Esc returns to the list. On a commit's details, Esc goes back.

While the view is maximized, restoring the view comes before leaving the screen, so the reader stays on the screen. In the cases below, Esc goes to what is open, focused or being extended instead of restoring the view. It restores the view only once that is closed or has lost the focus:

- a dialog, popover or menu is open
- the focus is in a comment editor, a form, a toolbar or a listbox
- a range of lines is being extended from its button

The search fields are not in this list, because Esc has nothing to close in them. Esc in a search field therefore restores the view.

While line history replaces the diff, Esc restores the view. The history stays. Opening a thread's discussion also restores the view, because the discussion is in the tab under the maximized view.

When the view is maximized or restored, what is under the file heading stays under it until the reader uses the wheel, a pointer or a key. The diff's elements are not created again on either change, so open comment editors and opened lines are kept.

**File name on hover.** On every screen with a diff, three places show the whole path on hover: a file row, a folder row and a group in the file heading. That group holds the path, "n/total" and the line counts. The whole path shows whether or not it is cut. These three places use a MUI tooltip rather than the browser's `title`.

The tooltip is up to 640px wide and at most 80% of the window. The folders and the file name are on separate lines. The tooltip of a renamed file's row also has the old path above the folders and the file name.

When the file has threads, a file row's tooltip gives the thread count. When the file is reviewed, the tooltip says so. The thread mark and the reviewed mark therefore have no tooltips of their own. The tooltip does not explain the letter for the kind of change or the line counts.

Keyboard focus on a file or folder row also shows the tooltip. The path in the heading cannot take focus, so a reader using only the keyboard cannot see a cut path there. This is an accepted limit. A screen reader still gets the whole path, from the rows' accessible names and from the heading's full text.

**Table of contents of a file.** A button at the right end of the file heading, labeled "Show the contents of this file" or "Hide the contents of this file", controls the table of contents. The table lists places in the file's diff, for finding one's way in a long file. It opens as a column to the right of the diff, so the button sits at the right end, on the side where the table opens, as the file-list button sits at the left end, on the side where the file list opens. When the heading's controls do not fit beside the path, they wrap onto a row below it, and the button stays at the right end of that row. The table is on every screen with a diff.

Each hunk is an entry. An entry shows the number of the hunk's first line (new side when the line has one, otherwise old side) and the hunk's added and removed lines. A hunk is named by the function or heading Git gave in its header. Without one it is named by its first change, or by its first line when "Hide whitespace" leaves no change.

Definitions inside a hunk are entries too, because a long new file is a single hunk. They come from the diff's lines as "Hide whitespace" shows them. Unchanged lines opened between hunks are not included. In a Markdown file the definitions are headings. In other files they are functions, classes, similar definitions and SQL objects, found by the text patterns in `src/features/mergeRequests/diffOutline.ts`. The patterns can miss a definition or list something else. A definition on an added or removed line is marked + or −. In files other than Markdown, a definition on an indented line is indented in the table too. A definition with the same name as its hunk is not listed.

The table holds 300 entries at most. Beyond that it drops all the indented definitions. If that is still too many, it keeps 300 of the remaining entries at even steps.

Hunks are counted in those steps too. Because the kept entries are evenly spread, the highlight still moves to the end of the file. The steps count entries, not lines, so more entries remain where definitions are dense. The table says how many entries it left out.

Choosing an entry moves the page so that its line sits under the file heading. In a rendered Markdown diff, a hunk's entry moves to the rendered change block of the hunk's first change, and a definition's entry to the block nearest its line. An entry with no new-side line at or after it moves to the last block.

While the page scrolls, the last entry at or before the top of the visible diff is highlighted. The table scrolls itself to keep that entry in view. Until the first line or block reaches the file heading, the first entry is highlighted.

The highlight stays as it was when the top holds something other than a line of a hunk, such as a thread, a comment editor, a row of omitted lines or an opened line. A view change can keep the table's entries without scrolling the page, as wrapping long lines or opening lines do. Such a change leaves the highlight as it is until the next scroll or window resize.

In the table beside the diff, a chosen entry stays highlighted, because near the end of a file its line may not reach the top. It stays until the reader uses the wheel outside the table, presses a pointer or presses a key. A change in the entries also ends it, as on moving to another file or with "Hide whitespace". In the popover, the highlight starts from the current position each time it opens.

In a rendered Markdown diff the highlight moves by block. The block under the file heading decides the position. The highlight goes to the last entry at or before that block's first line.

Scrolling does not highlight an entry with no new-side line at or after it. The exception is the first entry while the first block has not reached the file heading.

The table is a 220px column at the right of the diff when 720px remains for the diff (848px for a side-by-side diff). The remaining width is the details pane's width, less the column and its gap, and less the file list's shown width and its gap when the list is shown. Widening the file list can therefore move the table into its popover. The file list keeps its own width rule, so it is not hidden to make room for the table. The column stays below the MR header and scrolls on its own. It is shown by default, the button hides and shows it, and the choice is saved on this device. With less width, the button opens the same table in a popover, whatever that choice is. The popover scrolls on its own and closes when an entry is chosen.

The button and the table are hidden in the whole-file view, while line history (opened from Blame) replaces the diff, for a diff that could not be parsed, and for a file with no diff lines.

The light and dark themes follow the OS setting at first launch, and a choice switched manually is saved on this device.

### Commit timeline placement

The timeline sits directly under the "Changes" tab, above the file list and the code diff. This does not reduce the width of the code, and the comparison target stays visible when the file is switched. The first item, "Entire MR", is an aggregate view, and the commits after it are in chronological order. A commit's diff is always the changes from its parent. The timeline sticks 8px below the MR header, the same position where it rests, and follows the header's height, so it does not jump when it starts sticking. The exception is an alert above the timeline, which pushes it down until the alert has scrolled away.

Each item has a short SHA and a subject, and a long subject is truncated, with the full text in a tooltip. Even with many items, the strip does not wrap to several rows and moves with horizontal scrolling and step buttons. The left and right arrows move the selection, Home goes to Entire MR, and End goes to the last commit. The selected item is identified by color and a selected marker, and the comparison source and target are also shown directly under the timeline. Next to the display of the comparison source and target is the "Compare from version" selection, and choosing a past version shows the diff from that version to the latest as read-only (with a rebase note).

"Local changes" to its right shows the difference between the linked clone's working tree and the MR's latest as read-only. The cell says only that the clone is on another branch in two cases. The first is when the clone is on a branch other than the source branch. The second is when the clone is not on the source branch and does not contain the MR's head. Otherwise the cell lists, in this order, whichever of these apply: the count of uncommitted changes (changed and untracked files together); the count of unpushed commits, when the clone contains the MR's head; and "fetch needed" when the MR's head is not local, or "pull needed" when it is local but not contained. When none apply, the cell says there are no changes.

The reader can choose a range of items by dragging across them or with Shift+click. When the range ends at "Local changes", the difference starts from the commit just before the range instead of from the MR's latest commit. The difference starts from the MR's base when the range starts at the first commit, at the item that stands for commits not shown, or at the item right after the item that stands for the versions before a rebase. When the range starts at the item for the versions before a rebase, the difference starts from the earlier version chosen on that item.

When the clone is not linked, "Local changes" shows a folder input box and "Choose folder…". Choosing a folder links it immediately. Once the clone is linked, the area above the diff shows the folder, branch, HEAD, last-changed time and read time, with reload and unlink. The app compares the write times of the changed files in the work tree with the time of the newest unpushed commit. The newest time is shown as the last-changed time. When neither the changed files nor an unpushed commit gives a time, the last-changed time is not shown. "Whole file" and the expansion between hunks use the current contents of the working tree.

### Whole file display

Near the file heading is "Diff / Whole file". "Whole file" does not stitch excerpt diffs together; it shows the post-change content of the selected version from start to end. When Entire MR is selected, it is the MR's latest state, and when a commit is selected, it is the content at that commit, and the SHA is shown to tell them apart.

The display mode is kept when switching files and commits within the same MR. The whole text uses a single column of line numbers and normal code display, without the diff's deleted lines or added marks. It is split into pages of 1,000 lines; rendered Markdown is not split. Existing line comment markers are shown on the diff side. A new comment can be entered from either the diff or the whole text, specifying the file, old/new side, line and SHA. The whole text not yet fetched and an empty file are shown as different states, and when it is not fetched, an excerpt is not shown as the whole text. In the future real connection too, file fetching and the cache are tied to the commit SHA, and the displayed version is not mixed with the content of the latest branch.

## Experience priorities

1. The current connection, project and search target are clear at once.
2. The reader can compare while watching the list, and the context remains after returning from the details.
3. No data, not fetched, updating, stale and failed to fetch can be told apart.
4. Daily operations can be repeated with both mouse and keyboard.
5. Input, switching and scrolling do not stop even with many MRs, diffs and discussions. The update status is visible even after cached content is shown.

Instead of designing new decoration per screen, the four structures of search, list, details and settings are reused. A large hero or statistics cards are not the default top screen.

A row of one-line items (text, chips, buttons, icons) centres them; text of two sizes in equal grid line boxes then sits within half a pixel of a shared baseline, so rows never use baseline alignment, which stretches the row by that half pixel. A mark (an icon, an avatar, a state marker, a control group) beside content that can take more than one line sits on that content's first line, never in the middle of the block: the row is `align="top"` and the mark is wrapped in `firstLine(line)`, a box as tall as the first line that centres it, where `line` is the first line's text variant (`'body1'`, sized from the theme's `typeLines`) or grid steps for a line set by controls. Panels of different heights side by side also use `align="top"`. `npm run design:guard` rejects a row `Stack` written by hand, `alignItems` on a `Row` or `Bar`, a flex `Box` that leaves its alignment unsaid, baseline alignment, and top alignment written by hand in a row. Latin and Japanese text share one centre in the middle of the line box: Latin is Segoe UI through balanced faces in `public/boot.css` (ascent and descent rebalanced, their sum unchanged), Japanese, Chinese and Korean are the bundled App Sans JP, SC, TC and KR, Noto Sans CJK with its outlines moved down to Segoe UI's centre, measured on each language's interface text (`scripts/build-fonts.py`, OFL in `public/fonts`), so mixed scripts stay aligned too; `tests/visual/text-centre.visual.ts` draws each language's interface text with the real fonts and checks both. Chrome puts baselines on whole pixels, so that centre sits 0.1 to 0.6px from the exact middle depending on the size |
| Corner radius | Small 4, standard 8. Arbitrary per-screen changes are prohibited |
| Color | canvas/surface/text/border/action and status colors. No strong colors without meaning are added |
| Motion | Short state changes, about 100 to 160ms, with one longer exception, the completion animation below. Follows reduced-motion. Screens in a `KeepAlive` (all but settings) fade in over 150ms when they come into view; `KeepAlive` does this, so a screen does not add this fade itself. One `KeepAlive` holds the screens of the list pane, one holds the open MRs, and one holds the tabs of an MR. Within one, and when an MR opens over the list, what was showing stays underneath so no blank pane shows. It stays while a screen shown for the first time builds out of sight (1s at most), then through the fade, and is removed when the fade ends, or 500ms after the fade starts if the end is never reported. An MR or its Discussion tab waiting out of sight also waits, within that 1s, for cached threads and the code excerpts beside the threads around the opening position, so these arrive together; the other threads mount afterwards. `KeepAlive` does the waiting, and reads join it through `useScreenReadiness`. Any other switch, such as back to the list from an MR or settings, has nothing underneath. Under memory pressure, the screen before still stays underneath until the new one has faded in, even when the screen before will not be kept afterwards. This applies to a switch within one `KeepAlive` and to an MR opening over the list. The list pane keeps the 6 lists most recently shown. Under memory pressure, it keeps only the list on view, and that list stays under an open MR. While settings is showing under memory pressure, it keeps only the list shown last. Content replacing a loading placeholder fades only where it calls `useFadeAfterLoading`: the thread list and the diff list on an MR's Discussion and Changes tabs, and each code excerpt beside a comment. Each counts separately, and timing starts once the cache check finishes, except for the diff list: once its placeholder has lasted more than 100ms, the content fades from 40% opacity over 150ms, because starting from 0 would dim the pane first; before that, it appears at once. A code excerpt's placeholder holds the excerpt's height, and its loading text shows only after 200ms, so code arriving between 100 and 200ms fades in without the text having shown. Menus, popovers, tooltips and toasts fade in and out instead of scaling, and list rows fade their hover (100ms). Only the completion of approve, merge and publishing a review paints the notification in the success color, and the check bounces while a ring expands (about 0.6 seconds, static under reduced-motion) |
| Icon | One icon per meaning, and one meaning per icon. State icons in a row are 16px. The mapping is below |

Icon mapping: project `Source`, directory `Folder`, file `InsertDriveFile`, parent folder `ArrowUpward`, branch `AltRoute`, commit `Commit`, commit history `History`, Merge requests `RateReview`, notifications `NotificationsNone` (when there is unread, the filled `Notifications` and a count tag), Settings `Settings`, open from a URL and link `Link`, connect to GitLab `Login`, token renewal `Key`, refetch `Refresh`, open externally `Launch`, pin (MRs only) `PushPin`, favorite (projects only) `Star`, approved (state) `ThumbUpOutlined` (the user's own approval is the filled `ThumbUp`), Draft `EditNote`, unread `MarkChatUnread`, default branch `Home`, protected `Lock`, merged `CallMerge`, archived `Inventory2`, pending review `ScheduleSend`, notification kinds (assigned `AssignmentInd`, mention `AlternateEmail`, approval request `HowToReg`, review request `PersonSearch`, mark `BookmarkBorder`, CI failure `ErrorOutline`, unmergeable `Block`), approve (action) `Check`, success `CheckCircleOutline`, error `ErrorOutline`, warning `WarningAmber`, waiting `Schedule`, cancel, close and cancel job `DoNotDisturbAlt`, rerun job or pipeline `Replay`, run manual job `PlayArrow`, toggle file tree display `ViewSidebar`, table of contents of a file `Toc`, tree view `AccountTree`, previous/next file `KeyboardArrowLeft/Right`, previous/next unresolved thread `KeyboardArrowUp/Down`. The resolved state of a thread is shown and switched by `ResolveToggle` (unresolved `RadioButtonUnchecked` / resolved `CheckCircle`).

**State is shown by shape and color rather than text.** To lower cognitive load, states lined up in list rows (MR state, Draft, CI, approval, unread, branch and project attributes) are not text chips but are shown with `StateIcon` (a 16px icon, with only a count added if needed). The state name stays in the tooltip and the name for assistive technology, and states are told apart by shape as well, not by color alone (the user's own approval is a filled icon, CI running spins, and it stops under the reduce-motion setting). Notification kinds, pending reviews on the diff, and the mergeability in the MR header are also icon-only, with the kind or reason in a tooltip. MR state and Draft add a short text to the icon in the header and preview.

These are values to be fixed after checking with lists of real data. The accent color is provisional, and state is not conveyed by color alone. Not connected is distinguished as neutral, a communication failure as error, and updating as progress. Light and dark use the same layout and information hierarchy.

## Search screen

From the top: "search target and input", "filters", "search results and fetched range". Project search and MR search are separated by tabs, and it is never ambiguous which one is being searched. Initial conditions such as all states / not merged are not hidden.

A result row shows not only the title but the namespace/project, MR number, state, author and update time. Projects with the same name and the same MR number in different projects can be told apart. The full body text is not fetched or shown in the list. An empty result shows the applied conditions and how to remove them.

"All 30" and "30 fetched" are distinguished. Server search, previous search results and search within saved data are switched explicitly. The order of search results follows the sort condition of the API used, and unrelated local history is not mixed into one ranking.

## Review screen and large data

The MR details share the tabs Discussion, Changes and Overview, and restore file selection, position and expansion state on Back. A search of the title/description is not confused with showing comments. The Changes tab is centered on the selected file, and resolved discussions are folded. Additional loading and truncated states are not hidden.

The normal review operations are overall/line comments, replies, editing and deleting one's own comments, resolve/reopen, publishing drafts, and approve/revoke. Text input, saving and send states are unified in ReviewComposer. The approval state is kept separate from the comment send state. "Viewed" files are labeled as local progress, and the reader is asked to check again when the diff version changes.

The draft list distinguishes local saves from server saves. The body and count to publish can be checked, and drafts created on the web are not published implicitly. A partial success of publishing several is shown per item. An unknown post result is distinguished from a failure, and the reader is not led to resend before checking.

With a cache, the content is shown immediately, and a full-screen Skeleton does not return during updating. Only the threads changed by a post or resolve are updated, and the list position and input text are kept. When permission expires, the cached display continues and is not bypassed.

No list, diff or discussion is virtualized: rendered rows stay in the DOM. Off-screen MR list rows, diff pieces and discussion threads skip layout and paint with `content-visibility: auto`; the Diff section above names the diff pieces excepted. Check that the scroll position does not jump even with variable-height bodies, that the keyboard can move to items not yet rendered, and that a draft being edited does not disappear. Detailed performance targets and load sizes follow section 14 of [Architecture](architecture.md).

**Long discussions.** A discussion's threads normally mount together. The exception is when more than 12 threads are new to the list in one update (the threads of a discussion being opened or of an older page, read from the cache or from GitLab), unless the tab was built again at a saved position, as described below. Then these mount at once: the thread it opens at and the last thread, with the 4 on each side of each; and the threads of a linked or jumped-to comment, a comment being edited, a reply being written and a thread read on its own. "The thread it opens at" is the one the opening rule above picks.

Each other thread shown by the filter keeps a box of about its height and mounts later, one at a time: first those within 1,000 px of the view, then from the end of the list. The box is the height of the thread's header, plus 110 px per comment row shown when the thread is open (folded replies count as one row). Scrolling quickly can show such an empty box until its thread mounts. Moving with N, P or the thread outline to a waiting thread that is open mounts it at once and focuses its first comment. A folded one is only scrolled to and waits for its turn.

While threads mount, what the discussion opened at stays still until the reader scrolls, presses a key, clicks or moves to a comment. After that, the thread at the top of the view is kept still instead, as when older pages load. Threads skip layout and paint only after all have mounted, so that each keeps its real height.

Under memory pressure, only the MR tab on view is kept, so a Discussion tab left and opened again is built again. It returns to its saved position. The position is a distance from the top, so the tab mounts all its threads together. Measurements are in the [validation record](validation.md), including why only one tab is kept.

The boundary between comment kinds, pending reviews, editing and deleting, and the features needed for the real connection follows the [comment and review parity policy](comment-review-parity.md). A draft being typed is distinguished from a pending comment already added to the review, and the publish dialog includes only what has been added. Markdown input defaults to rich input that shows the formatting in place, and can be switched to the Markdown view that edits the syntax directly. When rich input would change how the body renders (such as HTML), it opens in the Markdown view and does not rewrite the body without the user's action. The typography of rich input uses the same style as the body display.

## Keyboard and focus

- Ctrl+K: the entry for navigation/search. Esc: close a panel and return focus to the original control.
- Enter: apply the search term, or open the selected item. Conditions other than the search term (state, person, label, branch, updated date, project, group) are edited from "+ Add condition" or the tags and applied the moment they are chosen. Applied conditions, including the search term, are all shown as removable tags, and the sort order is not a condition, so it is chosen with a dropdown, not a tag. Global shortcuts (including Ctrl+K and Ctrl+O) are not intercepted while typing in a text input.
- ?: the shortcut list. In an MR, N/P move between unresolved threads and ]/[ between files.
- Tab: moves through visible controls in logical order. Focus is shown by an outline, not by color alone.
- When details open, focus goes to the heading, and on return, to the original row.
- Arrow-key operation of tables is implemented as a pattern of the list component. It does not depend on whole-row clicks alone.
- Asynchronous updates are announced modestly with aria-live, and periodic updates do not cause a large amount of reading aloud.

Each refetch of a list does not reset the scroll position or selection. When a row falls out of the target, the reason is shown, and the selection is not silently moved to another row.

## Change procedure for AI implementation

1. Before a new feature, check whether it can be expressed with the existing screen patterns and shared components.
2. Make a state table for the feature. A screen that works only in the normal case is not complete.
3. When a new shared component or variant is made, add state examples to the UI catalog.
4. Pass the theme, type and lint checks and representative behavior tests.
5. Check light and dark, narrow/normal width, long Japanese text and long paths, and keyboard operation.
6. When the look of a shared component changes, record this device's baseline with `npm run ui:snap` before the change, and check the screenshot diff of representative screens with `npm run ui:snap` after the change. Compare with the committed baselines before pushing, and rebuild them if the diff is intended; the steps are in [After a visual change](../README.md#after-a-visual-change) in the README. Font rendering differs per device, so the committed baselines are made in CI. Sections of the UI catalog with a `catalog-*` id are captured automatically.

Static checks add, to the current detection of hard-coded colors and direct HTTP, a rule that direct invoke is not used outside the IPC layer. Creating a MUI theme per screen is prohibited. Not every color and dimension is assumed to be guaranteed by regular expressions alone; shared components and review are used together.

Screenshot baselines are limited to representative states of the project list, past MR search, MR overview, diff, discussion and connection error. The OS, font and WebView2 version are recorded, so differences from renderer updates can be told apart from unintended layout differences. Data fixtures use anonymized fixed data.
